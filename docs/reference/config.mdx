# Config files

Everything csuite writes lands in one of three places: the broker's
directory, your user config directory, and your user cache/data
directories. All csuite-owned files are written at `0o600` in
directories created at `0o700`.

## The broker directory

`csuite setup` (or a first `csuite serve` at an interactive terminal)
creates a `./csuite/` directory — or uses `./csuite.json` in the
current directory if one already exists there:

```
csuite/
├── csuite.json           server config
├── csuite.db             team state — members, tokens, messages, objectives
├── csuite-activity.db    captured traces
└── csuite-kek.bin        encryption key (unless $CSUITE_KEK is set)
```

Override the config location with `--config-path` or
`$CSUITE_CONFIG_PATH`; relative paths inside the config resolve
against the config file's directory, so the whole directory can be
moved as a unit.

### csuite.json

A small infrastructure config — where the database lives and which
optional server features are on:

```json
{
  "dbPath": "./csuite.db",
  "https": { "mode": "off", "...": "..." }
}
```

Every key is optional and **omitted when unset** — the loader rejects
`null` (`expected string, received null`), so do not copy a key you
mean to leave at its default.

- `dbPath` / `activityDbPath` — database locations. Omit the activity
  path for the standard derivation from `dbPath`.
- `https` — TLS settings for serving beyond localhost.
- `webPush` — browser push notification keys, generated on first use.
- `jwt` — set by the [platform connect](/docs/self-hosted-connect)
  flow, via its own sidecar overlay file.
- `files` — shared file storage root and size limit.

**Team data does not live here.** Members, permissions, tokens, and
authenticator enrollments are rows in `csuite.db`, managed through
`csuite member`, `csuite team`, the web UI, or the API — never by
editing files.

### csuite-kek.bin

The key that encrypts secret values at rest (broker-held secrets,
authenticator secrets, push keys). Auto-generated on first boot unless
`$CSUITE_KEK` provides the key directly.

Losing it doesn't lose the team: bearer tokens are stored as hashes
and survive, but stored secret values and authenticator enrollments
become undecryptable — you'd re-enter secrets and re-run
`csuite enroll` per member. In production, back it up or inject
`$CSUITE_KEK` from a secrets manager.

### The databases

`csuite.db` holds everything the team is; `csuite-activity.db` holds
what the agents did (traces), kept separate so heavy trace writes
never stall the team. `csuite prune-traces` is the retention tool for
the activity side. Back up both files together.

## auth.json — the device auth store

Where `csuite connect` saves bearer tokens, and where every command
looks after `--token` and `$CSUITE_TOKEN`.

| OS | Path |
|---|---|
| Linux/BSD | `$XDG_CONFIG_HOME/csuite/auth.json` (default `~/.config/csuite/auth.json`) |
| macOS | `~/Library/Application Support/csuite/auth.json` |
| Windows | `%APPDATA%\csuite\auth.json` |

```json
{
  "schema": 2,
  "entries": [
    { "url": "https://broker.example.com", "workspace": "/home/you/projects/agent-a",
      "token": "csuite_...", "savedAt": 1754000000000 },
    { "url": "http://127.0.0.1:8717", "workspace": null,
      "token": "csuite_...", "savedAt": 1753900000000 }
  ]
}
```

The store deliberately keeps nothing else — no member names, no
labels. That metadata lives on the broker
(`csuite roster`, the web UI's token list).

Broker URL lookup is exact-match — no trailing-slash normalization.
Use the URL form you connected with.

### Workspace scoping

Each entry records the directory it serves (`workspace`), so one
machine can hold a distinct member identity per project. For a given
broker URL:

1. Among entries whose workspace contains the current directory, the
   **longest** workspace path wins — enrolling in a project root
   covers its subdirectories, and a nested enrollment overrides its
   parent.
2. Otherwise the unscoped entry (`workspace: null`), if any.
3. Otherwise a legacy project-local store (below).

Containment is by path segment, not string prefix, and symlinks are
resolved. `csuite auth list` shows every entry and marks the one that
resolves from where you are.

### Legacy project-local stores

Older versions wrote `.csuite/auth.json` inside the project directory.
Those files are still read as a last-resort fallback, so upgrading
never locks you out — but the location put a bearer token inside what
is usually a git repository.

`csuite auth migrate` folds a legacy store into the global one
(scoping its entries to the directory that held it) without deleting
the old file or displacing newer entries. If the legacy file sat in a
git working tree, treat the token as potentially published and rotate
it: `csuite rotate --member <name> --all --token-file <fresh-path>`.

## Runner working files

`csuite claude` and `csuite codex` keep their working state out of
your project — nothing in your working tree is created, rewritten, or
backed up.

- **Session logs** — `~/.cache/commandsuite/session-<pid>.log`, one
  JSON line per event. The path is printed at startup; `tail -f` it
  for live diagnostics.
- **Codex working config** — an ephemeral directory under
  `~/.cache/commandsuite/codex/`, created per run and removed on exit.
  It reuses your real `codex login` credentials without copying them.
- **Codex resume history** —
  `~/.local/share/commandsuite/codex/sessions/<member>/`, the durable
  thread history that makes `csuite codex --resume` work across runs.
