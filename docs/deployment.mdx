# Deployment

CommandSuite is one process — a broker with SQLite on disk — that
serves the API and the web UI from the same port. Three ways to run
it, one outcome each time: a broker, a seeded team, the web UI
reachable, and (for the last two) a runner member enrolled and ready.

| you have | run | you get |
|---|---|---|
| a terminal | `csuite serve` | the first-run wizard, then the broker on `http://127.0.0.1:8717` — [getting started](/docs/getting-started) |
| a server, a script, CI, an agent | `scripts/bootstrap.sh up` | the same, with no prompts — [headless setup](/docs/headless-setup) |
| Docker | `docker compose up` | the same, in a container, state on a volume — this page |

## `docker compose up`

From a checkout of the repository:

```bash
docker compose up -d          # builds the image, seeds, enrols, serves
docker compose logs -f csuite # watch the bring-up; ends at "listening on http://0.0.0.0:8717"
open http://127.0.0.1:8717    # the web UI
```

What the container does, in order, on first start — it is
[`scripts/bootstrap.sh`](/docs/headless-setup), unchanged, followed by
the broker in the foreground:

1. `csuite setup --non-interactive` — team `bootstrap`, first member
   `admin`, bearer token and TOTP secret written to the volume at mode
   0600.
2. The broker starts on loopback; `/healthz`, the web UI, an
   authenticated roster and a TOTP sign-in are checked.
3. A runner member `builder` is enrolled through the real device-code
   flow (`csuite connect`, approved from the CLI as `admin`); its
   credential resolves from `/var/lib/csuite/runner` with no
   environment variable; `csuite claude --doctor` passes (in this
   broker-only image, with the agent binary reported absent by design).
4. The loopback broker stops and the real one runs as PID 1 on
   `0.0.0.0:8717`. That is where the container stops: an enrolled
   runner member, not a running runner. A live runner needs a model
   credential and its own process lifecycle, so it runs **outside** the
   container — on any machine, `csuite connect --url http://<host>:8717`
   (approve as `admin`, from the web UI or `csuite connect approve`) and
   then `csuite claude` / `csuite codex` as a service:
   [always-on agent](/docs/guides/always-on-agent). Setting
   `CSUITE_START_RUNNER=1` on the container is refused with that message.

A restart re-runs the same sequence against the volume: already
seeded, already enrolled, a few seconds. The image contains no secret
and prints none; the CLI and broker build from this checkout.

### Reading the secrets

```bash
docker compose exec csuite cat /var/lib/csuite/secrets/admin.token   # bearer token for admin
docker compose exec csuite cat /var/lib/csuite/secrets/admin.totp    # base32 TOTP secret for the web UI
```

Use the token with `CSUITE_TOKEN=… csuite roster --url http://127.0.0.1:8717`
from your machine, or sign in to the web UI with a code from the
secret. Both files are the only copies; the broker stores hashes.

### Environment variables

All optional; set them in a `.env` beside `compose.yaml` or on the
command line.

| variable | default | what it does |
|---|---|---|
| `CSUITE_PORT` | `8717` | Host port mapped to the broker. |
| `CSUITE_TEAM` | `bootstrap` | Team name seeded on first start. |
| `CSUITE_ADMIN` | `admin` | First member (holds every permission); names the secret files. |
| `CSUITE_RUNNER` | `builder` | Runner member enrolled on first start. |
| `CSUITE_RUNNER_VERB` | `claude` | Which runner's preflight is proved: `claude` or `codex`. |
| `CSUITE_LOG_LEVEL` | `info` | Broker log threshold. |

Names and team are read only on the first start; later changes do
nothing until the volume is recreated.

### Volume and reset

Everything the container writes lives in the named volume
`csuite-state`, mounted at `/var/lib/csuite`: the server directory
(`server/csuite.json`, databases, KEK), `secrets/`, the runner
workspace and its auth store, and the file blob store under `data/`.
Back it up as a unit. To start over:

```bash
docker compose down -v        # removes the volume: team, tokens, files, traces
docker compose up -d
```

### Image

Two stages: a digest-pinned `node:22-bookworm-slim` builder, and a
digest-pinned Alpine runtime carrying the distro's `nodejs` (22.x),
`bash` and `curl`, the production dependency tree of the `csuite`
meta-package, and the bootstrap script, running as the unprivileged
`node` user — about 150 MB.

This is the **broker-only** image: the production install passes
`--no-optional`, which leaves out the Claude Agent SDK (an optional
dependency of `csuite-cli`, ~263 MB of per-platform agent binary the
broker never executes). Every broker verb — `serve`, `setup`,
`connect`, `member`, `fs`, the bootstrap path — works without it;
`csuite claude` inside the container fails fast naming the missing
package, and `csuite claude --doctor` reports the agent binary as
`absent by design` (advisory, not a failure) — the compose CI asserts
exactly that line. To build an image that can also run a live agent
in-container, remove `--no-optional` from the `pnpm install --prod`
line in the `Dockerfile`; the default install of csuite outside a
container is unaffected either way, because npm and pnpm install
optional dependencies by default.

No image is published; `compose up` builds `commandsuite/csuite:local`
from your checkout.

### Verifying a deployment

`scripts/compose-check.sh` is what CI runs and what a person can run:
`up`, the assertions above plus the in-container doctor line,
`restart`, the same again, `down -v`.
It stops before any live model connection and says so.
`KEEP=1 scripts/compose-check.sh` leaves the stack running.

## Beyond localhost

The broker serves plain HTTP on whatever it binds — `csuite serve
--host 0.0.0.0` (or the container's mapped port) is HTTP on the LAN.
TLS is a configuration choice, not a bind-address side effect: set
`https.mode` in `csuite.json` to `self-signed` or `custom` (see
[config files](/docs/reference/config)), or front the broker with
Tailscale Funnel, Cloudflare Tunnel, or any reverse proxy that holds a
real certificate. `127.0.0.1` is a secure context, so PWA install and
push notifications work there without a certificate. Pairing with a
hosted control plane: [self-hosted connect](/docs/self-hosted-connect).
