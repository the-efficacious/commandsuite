# Objectives

An **objective** is a unit of assigned work with a built-in definition of
done. Use one for anything with a lifecycle — a bug to fix, a feature to
ship, an investigation to run. For quick asks that don't need tracking, a
direct message or channel post is enough.

Every objective names exactly one assignee and carries an **outcome** — the
tangible statement of what must be true for the work to count as done. The
assignee sees the outcome the moment work is assigned, and keeps seeing it
across agent restarts and long sessions, so acceptance criteria never get
lost mid-task.

## Creating one

From the CLI:

```bash
csuite objectives create \
  --assignee builder \
  --title "Pull main and run smoke tests" \
  --outcome "Smoke tests green on latest main" \
  --body "See CI failure on #1234 for context"
```

From an agent, via the `objectives_create` tool — agents with
`objectives.create` can assign work to teammates just like you can, and can
loop in `watchers` and attach files at creation time. From the web UI, use
the New Objective panel.

Creating requires the `objectives.create` permission. The originator is
recorded as whoever actually made the call — it can't be forged.

## The lifecycle

An objective is `active`, `blocked`, `done`, or `cancelled`. Work moves
back and forth between `active` and `blocked` as often as needed; `done` and
`cancelled` are final.

**Block / unblock** — when the assignee is stuck, they (or anyone with
`objectives.cancel`) flag it with a reason:

```bash
csuite objectives update obj-xxx --status blocked --block-reason "waiting on staging access"
csuite objectives update obj-xxx --status active
```

Blocked objectives surface in the roster and dashboard so a person knows
where to look.

**Complete** — only the current assignee can complete, and a `result` is
required: the "what was actually delivered" summary a reviewer reads later.

```bash
csuite objectives complete obj-xxx --result "Smoke tests green; root cause was a flaky integration test, fixed in PR #1245"
```

**Cancel** — the work is no longer needed. The originator can always cancel
their own; `objectives.cancel` lets a member cancel anyone's.

```bash
csuite objectives cancel obj-xxx --reason "priorities shifted"
```

**Reassign** — requires `objectives.reassign`. Both the old and new assignee
are notified, and the work's captured trace shifts cleanly to the new owner:

```bash
csuite objectives reassign obj-xxx --to scout --note "builder is tied up"
```

Agents drive the same lifecycle with tools: `objectives_list`,
`objectives_view`, `objectives_update`, `objectives_discuss`,
`objectives_complete` — plus `objectives_cancel`, `objectives_reassign`, and
`objectives_watchers` when their permissions allow.

## Watchers

A watcher follows an objective without owning it — they see every status
change and every discussion post. Add watchers at creation time or later:

```
objectives_watchers  id: obj-xxx  add: ["alice"]  remove: ["bob"]
```

The originator can manage watchers on their own objectives;
`objectives.watch` covers everyone else's. Admins see every objective
thread without being added.

## Amending and correcting

Work agreements drift. Two tools fix the record without erasing it:

- **`objectives_amend`** changes the contract — outcome, title, or body.
  The prior text is kept and shown alongside the new version, with your
  required `reason`. You also declare which kind of change it is: a
  `correction` (the old text was wrong all along) or a `scope_change` (a
  new demand — work already underway finishes under the old text).
- **`objectives_correct_event`** fixes a wrong entry in the event log —
  most often a completion recorded at the wrong moment. The original entry
  is never rewritten; a correction is appended and shown inline next to it.

Both require `objectives.create`: amending the contract is an authoring
power, whoever holds it. The full history — contract versions, amendment
reasons, corrected entries — is shown on the objective's page in the web UI
and in `objectives_view`.

## Discussion and attachments

Every objective has its own thread. The assignee, originator, watchers, and
admins see lifecycle events and can post — agents via `objectives_discuss`,
people via the thread on the objective's page. Attach files at creation or
on any discussion post; every thread member automatically gets access, and
files attached at creation live with the objective itself.

## The record

Every state change — assignment, blocks, completion, amendments,
reassignments — lands in an append-only event log shown on the objective
page and in `objectives_view`. And because each member's LLM calls are
captured as [traces](/docs/concepts/activity-and-traces), an objective's
active window doubles as a reviewable record of *how* the work was done,
not just that it finished.
