# Tool sources

Give your agents tools for the systems your team already uses —
Jira, an internal API, a vendor's MCP server — without putting the
credential on any agent's machine. A **tool source** is registered
once on the broker; the broker holds the credential and offers the
tools to the members you choose. The only credential an agent
machine ever holds is the member's own token.

Two kinds:

- **`custom`** — tools you define yourself: a name, a description,
  an input schema, and an HTTP call to make. The broker executes
  each call against the third-party API, injecting the stored
  credential. Use this to wrap a REST API as a handful of
  purpose-built tools.
- **`mcp`** — a remote MCP server the broker connects to on your
  behalf. Its tools are discovered and offered to members, and calls
  are relayed. Use this when the provider ships an MCP server and
  you want the broker to hold its credential.

MCP tool sources must be reachable by URL from the broker. A local stdio
server running on an agent workstation cannot be carried by a tool source;
for Codex members, configure it through the runner's
[durable local MCP path](/docs/runners/codex#local-stdio-mcp-servers).

## How tools reach an agent

Bind a source to members and its tools appear in their toolbox,
named `<source>__<name>` (`jira__create_issue`). To the agent they
are ordinary tools. Each call goes to the broker, which checks the
member is bound, executes or relays it with the stored credential,
records it, and returns the result.

Two properties worth knowing:

- **Changes arrive live.** Add a tool or bind a member and running
  agents pick it up mid-session — no restart.
- **Upstream failures are readable.** An error from the third-party
  API comes back as a tool error the model can read and retry on.

## Who gets which tools

A member sees a source's tools when the source is enabled and the
member is bound to it (or the source is open to all members):

```bash
csuite tools bind jira scout        # just scout
csuite tools add search --kind mcp --url ... --all-members
```

There is no management bypass on calls — `tools.manage` holders bind themselves like
anyone else, so there is exactly one access rule.

## Credentials

One credential per source, sent as either a bearer token or a named
header:

```bash
csuite tools cred jira --bearer <token>
csuite tools cred jira --header X-Api-Key=<value>
```

Credentials are write-only — no command or endpoint ever returns
one — and encrypted at rest. Scope the credential at its source (a
narrowly-scoped PAT, a service account): that scoping is the real
control on what the tools can do.

## Custom tools

A custom tool is configuration, not code:

```json
{
  "description": "Fetch a Jira issue by key.",
  "inputSchema": {
    "type": "object",
    "properties": { "key": { "type": "string" } },
    "required": ["key"]
  },
  "binding": {
    "method": "GET",
    "urlTemplate": "https://your-org.atlassian.net/rest/api/3/issue/{{args.key}}",
    "resultPath": "fields.summary"
  }
}
```

`{{args.<name>}}` placeholders drop the agent's arguments into the
URL, headers, or body. The host part of the URL is fixed at save
time — an agent's arguments can never steer a credentialed request
to a different server, and the credential header can never be
templated. That holds through redirects too: a redirect within the
configured origin is followed, and one that leaves it fails the call
without sending anything, so an upstream that bounces cannot become a
way to read the credential. `resultPath` optionally extracts one field
from a JSON response so the agent gets the answer, not the envelope.
Responses are capped at 64 KiB.

## MCP sources

```bash
csuite tools add up --kind mcp --url https://mcp.example.com/v1
csuite tools cred up --bearer <token>
csuite tools refresh up                  # discover the upstream's tools
csuite tools bind up scout
```

Discovery is explicit: `refresh` lists the upstream's tools; a tool
added upstream later won't work until you refresh again (the error
says so). Upstream tool errors reach the agent as readable tool
errors; an unreachable upstream is reported as a server problem for
a `tools.manage` holder to fix.

## Every call is recorded

Each invocation is written to the calling member's
[activity stream](/docs/concepts/activity-and-traces) by the broker
itself — tool name, input, error flag, duration. The agent process
can't evade it.

## Administration

Managing sources requires the `tools.manage` permission. Four
surfaces: the web UI (Tools in the nav), the `csuite tools` CLI, the
[REST API](/docs/dev/rest-api), and the `tool_sources_*` tools in
the toolbox of agents holding the permission.

That last surface makes connector-building an agent task: a `tools.manage` holder
agent reads an API's docs, registers the source, writes the tool
definitions, binds itself, and test-calls until they work. The
common split is **AI builds the connector, human drops the key** via
the web UI, so the secret never enters the agent's context. Agents
*can* set credentials too — useful when the agent minted the key
itself — with the tradeoff that an agent-set value passes through
that session's transcript.

For credentials an agent's own command-line tooling needs locally
(`gh`, `terraform`, `npm`) — rather than tools the broker executes —
use [secrets](/docs/concepts/secrets) instead.
