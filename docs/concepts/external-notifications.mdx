# External notifications

Let the outside world reach your agents. An **external
notification** is an event from outside the team — a GitHub webhook,
a monitoring alert, a `curl` from your deploy script — that the
broker receives, verifies, and delivers to members or channels as a
message. CI goes red and the builder agent is reading the log before
a human noticed.

Three words, used consistently:

- **Endpoint** — the thing you configure. Each has a slug; senders
  POST to `https://<broker>/hooks/<slug>`.
- **Delivery** — one inbound request. Every delivery gets a receipt
  you can inspect and replay.
- **Profile** — a verification secret shared by several endpoints,
  so rotating one sender's secret is one change.

## Setting one up

```bash
# GitHub → the builder agent, queued while offline, bursts coalesced
csuite notifications add ci-alerts \
  --target @builder \
  --auth hmac-sha256 \
  --level warning \
  --template 'CI {{payload.state}} on {{payload.branches.0}}' \
  --if-offline queue --debounce-ms 120000 \
  --dedupe-header x-github-delivery
csuite notifications set-secret ci-alerts   # hidden prompt, or pipe stdin

# Point GitHub at:  https://<broker>/hooks/ci-alerts
```

(`csuite hooks` is an alias.) An endpoint can target members — each
gets their own copy — and/or channels.

## Verification

Two kinds, and both fail closed — an endpoint with no secret rejects
everything:

- **`hmac-sha256`** — the sender signs the request body. Defaults
  are GitHub-compatible; configure the header and prefix for Stripe-
  and Linear-style senders.
- **`header-secret`** — the shared secret sent verbatim in a header
  (default `x-hook-secret`), for senders that can't sign.

Verification secrets are write-only and encrypted at rest. A failed
verification returns a bare 401 to the sender; the specific reason
lands on the delivery receipt, where you can see it and an attacker
can't.

Unknown slugs and disabled endpoints return that same status and body,
so the unauthenticated surface discloses neither endpoint existence nor
administrative state. This deliberately makes a typo look like an auth
failure. An authorized operator uses `csuite notifications list|view`
or the Notifications UI instead. A correctly signed request to a
disabled endpoint creates a rejected receipt whose reason names the
disablement; an anonymous request to it creates no receipt.

The receipt for a failed verification records the size, SHA-256, and
reason — not the payload. Anyone can reach this endpoint, so anyone
who fails the signature check is by definition unauthenticated, and
their body is not something to keep. A rejected delivery cannot be
replayed for the same reason.

## What the agent sees

Delivered messages arrive from **`hook:<slug>`** — a sender name no
member can have, so external input is visibly foreign. The content
is wrapped in a frame stating where it came from, whether deliveries
were coalesced, and how long the message was queued. Agents are
briefed to treat framed content as information to act on per their
standing instructions — never as instructions itself. Your template
controls only what appears inside the frame.

## Filters and templates

Both optional, per endpoint:

- **Filters** — drop rules over the JSON payload
  (`{ path: "branch", op: "eq", value: "main" }`; ops: `eq`, `ne`,
  `in`, `exists`, `contains`; all rules must match). Filtered
  deliveries are receipted and reach nobody.
- **Template** — `{{payload.<dot.path>}}` substitution renders the
  delivered text; without one, the payload arrives pretty-printed.
  The raw body is kept on the receipt either way.

When you control the sender, shape the payload there and skip both —
these exist for the senders you don't control.

## Delivery policy

Set per endpoint; senders can override some knobs per delivery with
query parameters on the hook URL.

| Knob | Values (default first) | Override |
|---|---|---|
| `if-offline` | `drop` \| `queue` | `?if_offline=` |
| `if-busy` | `now` \| `wait` | `?if_busy=` |
| `debounce-ms` / `debounce-max` | `0` (off) / `20` | — |
| `queue-ttl-ms` | 24h | — |
| `max-wait-ms` | 15m | — |
| `level` | `info` | `?level=` |

**Debounce** merges a burst into one coalesced message. **Queue**
holds deliveries for an offline member until their runner next
connects; entries older than the TTL expire instead — stale news is
worse than none. **Wait** holds deliveries while the member is
mid-turn and delivers when it goes idle; `max-wait-ms` forces
delivery so a long turn can't starve the news. **`critical`**
punches through debounce and busy-wait.

The defaults (`drop` / `now`) make a delivery behave exactly like a
teammate's message; anything fancier is something you asked for.

## Receipts and replay

`csuite notifications deliveries ci-alerts` lists receipts newest
first: status, reason, and the message ids the delivery became — so
you can walk from external event to message to agent activity.
`csuite notifications replay <delivery-id>` re-runs a stored
delivery through filters, template, and policy (verification and
dedupe are skipped — replay is for debugging exactly those). A
delivery that failed verification cannot be replayed. Bodies are
capped at 256 KiB, each endpoint is rate-limited to 120 requests per
minute, and each keeps its most recent 1000 receipts — older ones are
dropped as new ones arrive. If an offline or busy queue spans that
boundary, references to the retired receipts are dropped from the queue
too; queueing cannot make durable receipt storage exceed the cap.

## Administration

Managing endpoints requires the `notifications.manage` permission.
Four surfaces: the web UI (Notifications in the nav), the
`csuite notifications` CLI, the [REST API](/docs/dev/rest-api), and
the `notifications_*` tools in the toolbox of agents holding the
permission. Any member can view the endpoints that target them.

`/hooks/*` is deliberately open at the door — the per-endpoint
verifier is the lock. If you front the broker publicly, `/hooks/*`
is exactly the surface you intend to expose.

## Patterns

The dividing line: **tools are capabilities exercised inside an
agent's turn; endpoints are triggers that exist outside any turn.**
Agent → world is always a [tool](/docs/concepts/tool-sources);
world → agent is always an endpoint — whether the world pushes, is
polled on the agent's behalf, or is simply the clock.

### The script driver

When you control the sender, skip providers entirely — a deploy
script, a Makefile target, a monitoring check posts directly:

```bash
curl -sf -X POST "https://<broker>/hooks/deploy-notify" \
  -H "x-hook-secret: $HOOK_SECRET" \
  -H "content-type: application/json" \
  -d '{"env":"prod","ok":true,"sha":"'"$(git rev-parse HEAD)"'"}'
```

Use `--auth header-secret` for these; HMAC buys nothing against a
sender you wrote yourself. Query overrides let the script steer per
event: `?level=critical&if_busy=now` for the page-worthy path,
defaults for the routine one.

### The self-provisioned poller

Agents can't poll: an idle agent isn't running, so there is no loop
in which a "check the mailbox" tool call could happen. And the
obvious workaround — DMing yourself from a cron script — is
deliberately dead: agents filter chat messages from themselves so
they don't loop on their own output.

The supported shape closes the loop through the front door. An agent
holding `notifications.manage` wires it end to end from its own
toolbox:

1. `notifications_create` — an endpoint targeting **itself**, with
   `header-secret` auth and `if-offline: queue` so nothing is lost
   across restarts.
2. `notifications_set_secret` — mint a long random value.
3. Write a cron script on its own machine that checks the source
   (IMAP, an API, a directory) with **local** credentials and, only
   when something is new, POSTs it to the hook.
4. Debug with `notifications_deliveries` and `notifications_replay`
   until events flow.

The cadence lives in cron, where idle checks are free — model tokens
are spent only when a real event starts a turn. Credentials for the
polled source stay on the agent's machine; the broker never holds
them. The caveat is durability: the script lives on one machine and
nothing on the broker shows it exists. For team-critical sources,
prefer a sender an operator owns.

### The anti-pattern: staying awake to poll

A sleep-poll loop *inside* a turn technically works and is quietly
terrible: the context window grows with every idle check, the member
reads as perpetually working (so `if-busy: wait` deliveries from
every other source are held against it), and you pay for a live turn
around the clock. The external-script shape gets the same cadence
with none of that — the agent is genuinely idle between events.
