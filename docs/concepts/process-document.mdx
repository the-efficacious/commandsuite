# Process document

Write down how your team works — the merge model, what counts as
verification, who signs off — once, in one document that every agent
carries in its standing context.
[Objectives](/docs/concepts/objectives) carry the contract for one
piece of work; the process document carries the contract for all of
it.

There is at most one per team, and it is authored: a person or agent
writes and edits it the way they would a README.

## Why a document and not an announcement

A rule announced in chat is not a rule anyone can be held to. Chat
history is the first thing an agent's context loses over a long
session, and a member who joins later never saw it. The process
document closes that gap by living in every agent's **standing
context**, delivered at session start:

- What a member has is always the current version.
- A member who never saw the announcement still has the rule.
- No agent has to remember to check.

A team that has never written one isn't silent about it — agents see
an explicit *"no process document has been set for this team"* line,
so a missing document is never mistaken for a broken delivery.

## Editing

Editing requires the `process.manage` permission, which ships
granted to nobody. Whoever holds it can rewrite what binds every
member, so who holds it is a deliberate decision. Edit it in the web
UI, over the [REST API](/docs/dev/rest-api), or — for agents holding
the permission — with the `process_document_write` tool.

Two things to know before you edit:

- **A write replaces the whole document.** Read it first and send
  the complete new text — sending just a paragraph deletes
  everything you didn't retype.
- **Every edit records who, why, and what it replaced.** The reason
  is required: it's what a reader six weeks from now has instead of
  the conversation you were in. The full prior text is kept.

Each edit also declares whether work already underway finishes under
the old process:

- `correction` — retroactive. The prior text was wrong and was never
  validly binding.
- `scope_change` — forward-only. Work already started finishes under
  the prior text.

This is the same distinction objective amendments use, so "does
in-flight work follow the old rules?" has one answer everywhere.

## Size and history

The document is capped at 16,384 characters — it rides in every
member's context in every session, so its length is a cost everyone
pays. Keep it tight; superseded content should leave, not pile up.

Agents carry only the current text. Every prior version is kept in
the edit history — in the web UI, over the API, or via the
`process_document_history` tool — so editing fifty times costs
exactly what editing once costs.

## When edits take effect

An edit doesn't wait for the next session. Every agent whose
standing context changed finishes what it's doing, restarts, and
resumes the same conversation under the new text. Until an agent
has restarted, the roster reports it as restart-pending, so you can
see who is still running on the old text.

Separately, if the document drops out of a running Claude Code
session entirely (long sessions compact their context), the broker
notices and re-delivers it on a later turn. Codex sessions can't be
checked mid-flight that way, so a dropped document comes back for
them at the next restart.
