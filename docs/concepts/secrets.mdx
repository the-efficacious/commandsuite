# Secrets

Give an agent's command-line tooling the credentials it needs —
without pasting keys into shell profiles on every machine. A
**secret** is a value held on the broker and injected into the agent
process as an environment variable when a session starts. The
agent's tools — `gh`, `terraform`, `npm publish`, anything that
reads an env var — find the credential where they expect it, while
the value never appears in prompts, standing instructions, or the
session transcript.

A `secrets.manage` holder drops the key once; every runner for the bound members
picks it up at start, on any machine:

```bash
csuite secrets add gh --env GITHUB_TOKEN --description "org CI PAT"
csuite secrets set-value gh          # prompts without echo; or pipe stdin
csuite secrets bind gh scout
```

On scout's next `csuite claude` or `csuite codex` start, the runner
fetches its secrets over its authenticated connection and puts them
in the agent's environment. The agent just sees `$GITHUB_TOKEN`.

For values that *aren't* confidential — git identity, a region name,
a feature flag — use a [variable](/docs/concepts/variables) instead:
same delivery, but readable and never redacted from traces.

## How delivery works

- A member receives a secret when it is enabled and the member is
  bound (or the secret is open to all members). There is no management
  bypass — admins bind themselves like anyone else.
- Values are delivered only to the bound member's own runner, and
  every delivery is logged by name — never by value.
- Secrets are resolved **once, at session start**. Rotating a value
  or changing bindings takes effect on each member's next start; the
  change event in the secret's thread says so.
- `--no-secrets` on either runner command skips delivery entirely.

## Write-only, encrypted at rest

A secret's value is set via the CLI, the web UI, or the API — and
never returned by any of them. Listings show only that a value
exists. At rest the value is encrypted; setting values fails closed
if the broker's encryption key isn't active.

## Guardrails

- **Reserved names.** The env name must be an uppercase POSIX name,
  and names the runner itself manages (`CSUITE_*` and the agent
  runtimes' own variables) plus loader-control variables (`PATH`,
  `LD_*`, `NODE_OPTIONS`, …) are rejected. Without this, a secrets
  `secrets.manage` holder could break capture or gain code execution on every runner
  machine.
- **One value per member per variable.** A member can never resolve
  two values for the same env name — the check runs when you bind,
  and spans [variables](/docs/concepts/variables) too, since both
  land in the same environment. Two secrets *may* target the same
  name for different members, which is how every agent holds its own
  `GITHUB_TOKEN`.
- **Redacted from traces.** Secret values are scrubbed from
  everything captured into
  [activity and traces](/docs/concepts/activity-and-traces) — an
  agent that runs `env` or `echo $GITHUB_TOKEN` leaks `[REDACTED]`
  into the stored record, not the key. Variable values are not
  scrubbed; that is the whole difference between the two stores.
- **Never put a secret value in standing instructions.** Team
  context, role descriptions, personal instructions, and the
  [process document](/docs/concepts/process-document) are kept
  intact in captured traces so CommandSuite can verify they reached
  the agent. Write `$GITHUB_TOKEN` there if you must reference it,
  and keep the value in the secrets store — the write APIs warn if a
  block contains a registered secret value.

## What this protects — and what it doesn't

Environment delivery keeps secrets out of prompts and stored traces.
It does **not** keep them from the agent: anything in the
environment is readable by any command the agent runs, and once an
agent echoes a value into its own context, the model has seen it.
Two consequences:

- Scope the credential at its source — a narrow PAT, a dedicated
  service account.
- For credentials the agent should never be able to read at all, use
  a broker-executed [custom tool](/docs/concepts/tool-sources)
  instead: the credential stays on the broker and only results reach
  the agent. Secrets are the complementary primitive, for when the
  agent's own tooling needs the value locally.

## Administration

Managing secrets requires the `secrets.manage` permission. Four
surfaces: the web UI (**Environment** in the nav, where secrets sit
alongside [variables](/docs/concepts/variables)), the `csuite secrets` CLI,
the [REST API](/docs/dev/rest-api), and the `secrets_*` tools in the
toolbox of agents holding the permission.

Agents can set values too (`secrets_set_value`) — useful when the
agent minted the token itself — with the tradeoff that an agent-set
value passes through that session's transcript. For human-held keys,
the better split is **AI wires up the secret, human drops the
value** via the web UI, so it never enters agent context.

Registry changes notify the affected members — never carrying the
value — which doubles as the "restart your runner to pick this up"
signal.
