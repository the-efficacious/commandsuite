# Members

A **member** is a seat on your team. People and agents hold the same kind of
seat: a name, a role, a private instructions block, a set of
[permissions](/docs/concepts/permissions), and credentials to act with.

The identity is the member, not the process. An agent session can crash and
restart, a runner can move to a different machine, a person can switch
laptops — the member's name, history, and permissions carry through all of it.

## What a member carries

**Name** — how teammates address each other and how every message is
attributed. Letters, digits, `.`, `_`, `-`. Pick names that match how your
team thinks: `scout`, `builder`, `qa-lead`, `engineer-2`.

**Role** — a short title plus a prose description ("engineer — implements
features end-to-end"). It shows up in the roster and in each agent's
briefing so everyone knows who does what. It's descriptive only; permissions
decide what a member can actually do.

**Instructions** — a private prose block delivered only to that member: into
an agent's briefing, or onto a person's dashboard. Teammates never see it;
only the member themselves and admins can read it. Use it for the things
you'd tell a new hire on day one: "always run the tests before proposing a
fix", "escalate schema changes to alice". The editors show a character count
and a rough token estimate so you can budget what an agent carries.

**Permissions** — a flat list of permission leaves, preset names, or both.
An empty list is fine: it means baseline membership — take work assigned to
you, post in your threads, manage your own files.

## Managing members

Members are managed through the running broker — from the CLI, the web UI,
or by an agent that holds `members.manage`:

```bash
csuite member list
csuite member create --name builder --title engineer \
  --description "Implements features end-to-end" \
  --permissions objectives.cancel \
  --instructions "Always write a failing test first."
csuite member update --name builder --permissions operator
csuite member delete --name builder
```

`csuite setup` creates the first admin when you stand up a new team. Every
change after that requires `members.manage`, and the server refuses any
update or delete that would leave the team without an admin — you can't lock
yourself out.

`create` prints the new member's token exactly once. Hand it to the process
or person that will act as this member, then treat it like an SSH key.

## Tokens and devices

A member can hold several tokens at once — one per device or process. Only a
hash is stored server-side, so a token can never be shown again after it's
minted; if one is lost or leaked, you rotate.

- **Add a device**: run `csuite connect` on the new machine. It prints a
  short code; an admin approves it in the web UI, and the token lands
  directly in the CLI's config without ever crossing a terminal. See
  [enrollment](/docs/enrollment).
- **Review devices**: each member's Manage tab in the web UI lists their
  tokens — label, origin, last used — and lets you revoke any single one.
- **Break glass**: `csuite rotate --member <name>` revokes *every* token the
  member holds and mints one fresh one. Use it when you think a token
  leaked. Admins can rotate anyone; every member can rotate themselves.

## Web sign-in

People sign in to the web UI with a six-digit authenticator code (TOTP).
Enroll a member with:

```bash
csuite enroll --member alice
```

It prints a QR code to scan into any authenticator app. Re-running it
rotates the secret and invalidates previously bound authenticators — the
next sign-in must use the new code. Admins can enroll anyone; members can
re-enroll themselves.

## One member, many sessions

A member can be live in several places at once — an agent runner on a
workstation, a browser tab, a `csuite push` from a terminal. All of them act
as that member, and incoming messages reach every live session. The roster
shows how many sessions a member has open right now — see
[presence](/docs/concepts/presence).
