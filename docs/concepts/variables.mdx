# Variables

Put non-confidential values into an agent's environment the same way
you deliver [secrets](/docs/concepts/secrets) — git identity, a
region name, a non-secret endpoint, a feature flag. A **variable**
is held on the broker and injected into the agent process as an
environment variable at session start, exactly like a secret, with
two differences:

- **Its value is readable.** `csuite variables view` prints it back
  to a caller with the `secrets.manage` permission. A secret's value
  never comes back from anything.
- **It is never redacted.** Variable values appear verbatim in
  captured [traces](/docs/concepts/activity-and-traces); secret
  values are scrubbed.

```bash
csuite variables add author-name --env GIT_AUTHOR_NAME
csuite variables set-value author-name --value "Ada Lovelace"
csuite variables bind author-name scout
csuite variables view author-name        # prints the value back
```

Variables exist because storing a public value as a secret does real
damage: the value gets scrubbed from every captured trace. A git
author name stored as a secret erased that agent's own name from its
own traces. If a value isn't confidential, it shouldn't be redacted
— so it shouldn't be a secret.

## Choosing between a secret and a variable

**Use a [secret](/docs/concepts/secrets)** for anything
confidential: tokens, keys, passwords, signing material. Values are
encrypted at rest, write-only, and redacted from captured traces.

**Use a variable** for values that are already public, or that you'd
be fine reading in a trace: git identity, a region name, a
non-secret endpoint, a feature flag.

The test is not "is this sensitive?" but **"would I mind seeing this
in a captured trace?"** A variable's value is stored readable and
deliberately not redacted — putting a credential in one publishes it
to every trace the agent produces.

## Git identity migrates automatically

`GIT_AUTHOR_NAME`, `GIT_AUTHOR_EMAIL`, `GIT_COMMITTER_NAME`, and
`GIT_COMMITTER_EMAIL` move from the secrets store to the variables
store automatically when the broker starts, carrying their values
and bindings. There is no operator step — a manual step left undone
would keep scrubbing names from traces, and nothing would tell you.
A row that can't be moved (no stored value, or the broker's
encryption key isn't active) is named in the boot log rather than
dropped.

## One environment, two stores

Secrets and variables land in the same environment, so they share
one rule: **a member can never resolve two values for one
environment variable name**, regardless of which store they come
from. Binding a variable that would collide with a secret for the
same member — or the reverse — fails and names the rival:

```
scout already resolves GIT_AUTHOR_NAME from secret "scout-git-author-name"
```

A collision is an error, never a precedence rule — there is no
silent winner to remember. The same env name in both stores is fine
when they reach different members.

## Administration

Every change requires the `secrets.manage` permission — configuring
the team's runner environment is a privileged act whether or not the
value is confidential. Reading a variable's value takes the same
permission; other members see only that a value exists.

Four surfaces: the web UI (**Environment** in the nav, where
variables sit alongside secrets), the `csuite variables` CLI, the
[REST API](/docs/dev/rest-api), and the `variables_*` tools in the
toolbox of agents holding the permission.

The web UI shows both stores on one page because they share one
namespace — a member can never resolve one env var name from two
entries, and the broker enforces that across both stores, so a
collision raised while editing a secret names a variable. The two
still sit in separate labelled sections: which store a value lives in
decides whether it is scrubbed from captured traces, and that is a
safety property, not a filing detail.

There is no convert action between the two stores. Moving a variable
to a secret means deleting it and registering the secret; moving a
secret to a variable means the same, but you need the original value
to hand — a secret's value is write-only, so nothing on any surface
can read it back to carry it across.

Delivery works exactly like secrets: enabled and bound (or open to
all members), resolved once at session start. Changes take effect on
each member's next runner start, and every change notifies the bound
members saying exactly that.
