# Review an agent's work

By the end of this guide you'll be able to take any completed
contract and answer, with evidence: what was the agent told, what
did it actually do, what did it cost, and is the record accurate?
That loop — author, execute, verify, correct — is the accountability
story the rest of the product exists to support.

## 1. Start with the contract record

A contract is a fold over the annex, so its record is every event
that was ever written about it — the specification and any
amendments, attempts, verdicts, asks and rulings, lifecycle changes,
and discussion. Open the **Board** in the web UI and select the
contract, or read the same thing over the API:

```
GET /spine/contracts/<id>
GET /spine/events?contract=<id>
```

Agents read it with `annex_read`, filtered by contract. Every event
carries its captions — who acted, when, on which subject, at which
revision, and which events it cites.

{/* media: screenshot review-contract-detail — a contract detail view showing criteria with their verdicts, the current state, and the event stream below */}

Read the **criteria** first, and each criterion's verdict. That is
the whole check: the criteria were what the world had to become, and
a verdict is a verifier's judgement — `met`, `unmet`, or
`cannot_verify` — reached at a named revision, with evidence. A
completed contract with a verifier named could not have been
completed at all unless cited verdicts (or a ruling waiving a
`cannot_verify`) covered every criterion at one revision. With no
verifier named, the completion result stands alone and the record
says so — which is itself worth noticing during a review.

Two rules make the record worth trusting, and neither is a
permission anyone can be granted past: a verdict from the contract's
own **assignee** is refused, and a ruling from anyone but the ask's
named **authority** is refused.

## 2. Open the trace

The contract tells you what was committed to and what was judged; the
trace tells you what the agent actually did. Open the assignee's
member profile and select **Activity** for their timeline — every
model call and tool action captured while they worked, bracketed by
`session_start` / `session_end`. The capture comes from each agent's
own instrumentation, with no proxy or traffic interception — see
[Trace capture](/docs/tracing) for how, and
[Activity and traces](/docs/concepts/activity-and-traces) for what
each row means.

There is no per-contract trace view. Traces are per member; use the
contract's own timestamps to know which stretch of the timeline to
read.

Reading someone else's trace requires the `activity.read`
permission; every member can always read their own. No relationship
to the work grants it — being the author, the verifier, or the
authority on a contract tells you nothing about the assignee's model
calls. Record visibility and trace visibility are separate grants.

Each turn row shows the model used, the token counts, the agent's
response — its reasoning, the text it produced, the tools it called
and what they returned — and the full input context that produced
the call. That last part is the piece chat logs never give you: not
just what the agent said, but exactly what it was looking at when it
said it.

## 3. Understand the numbers

Turn rows carry usage like:

```
in=48210 out=612 cache_hit=45876
```

- `in` — tokens the model read for this call. This grows with the
  conversation: a long session pays for its history on every turn,
  which is why input dwarfs output on mature sessions.
- `out` — tokens the model generated.
- `cache_hit` — the portion of the input served from the provider's
  prompt cache. Providers bill cached reads at a steep discount, so
  a high `cache_hit` relative to `in` is the healthy shape.

CommandSuite reports counts; it does not convert them to money.
Multiply by your provider's current per-token pricing — and when
comparing contracts, compare total tokens across the trace, not
turn counts. Ten cheap turns can cost less than one turn dragging a
bloated context.

## 4. Know what redaction did — and didn't do

Traces are redacted before they leave the agent's machine:

- **Broker-held secrets never appear.** The values injected from the
  [secrets](/docs/concepts/secrets) store are known to the runner,
  and any occurrence in captured content is replaced — an agent that
  echoes a secret leaks `[REDACTED]` into the trace, not the value.
- **Recognizable credentials are scrubbed** — well-known API key and
  token formats are pattern-matched and replaced, and authorization
  headers are stripped. The credential the runner itself uses never
  appears in captured content.

What a redacted trace still contains: everything else. Full prompts,
file contents the agent read, tool output — the trace is useful
*because* it's complete. Which is also the honest limit of redaction:

- **Variables are not redacted**, by design — they exist precisely
  for config values that are safe to read in a trace. If a value
  shouldn't appear in one, it belongs in secrets, not
  [variables](/docs/concepts/variables).
- **An unrecognized secret is not caught.** A password pasted into
  chat, in no known format and not held by the broker, flows through
  verbatim. Redaction is a seatbelt; `activity.read` is the lock.
  Grant trace access as deliberately as you'd grant access to the
  underlying systems.

## 5. Correct the record, don't rewrite it

Review sometimes finds the record wrong: a criterion that was amended
verbally but never in writing, or a completion recorded at the wrong
revision. Nothing edits the annex. Two shapes of repair exist, and
both append:

**Amend the contract** — `contract_amend` changes the title,
criteria, or constraints. It requires `spine.author`, a `reason`, and
a `disposition`, and the disposition is a real decision:
`correction` means the prior text was wrong and work was never
validly held to it; `scope_change` means a new demand — work already
underway finishes under the old text. If you can't say which, you
haven't finished thinking about the amendment. `criteria` and
`constraints` are complete replacements rather than patches, and two
refusals are worth knowing before calling: removing text without a
`disclosure`, and dropping a criterion that already carries a verdict
without citing that verdict. Neither refuses the change — they stop
it happening quietly.

**Staple a correction** — a `correction` event names the event it
corrects and is appended beside it, so the original is never
rewritten and nobody reads the stale version innocently. The classic
case: a completion recorded at a PR head instead of the merge commit.
An agent reaches this by `promote`-ing the discussion post where the
mistake was noticed, `as: correction` — which makes the record show
where the correction actually came from rather than presenting it as
having arrived fully formed. Correcting what *happened* is not a
change to what was *required*, and it moves no contract version.

Because the durable fields carry no length caps, neither repair has
to be terse. Caps in this system scale **with** durability: the
roomiest fields are the permanent ones.

## 6. Prune what you no longer need

Activity is the heaviest data the broker stores — a busy agent
produces megabytes of trace per hour. Retention is yours to choose:

```bash
csuite prune-traces --older-than 30d
```

It shows the cutoff and row counts and asks before deleting; pass
`--yes` in scripts. Pruning removes captured activity older than the
cutoff — the annex is a separate store, and contracts, verdicts,
rulings, amendments, and corrections are untouched. The
accountability trail outlives the raw trace.

## Where this breaks

- **A trace can be incomplete — but it says so.** Capture is
  accounted end to end: each session's run summary records what was
  captured versus dropped, so a gap shows up as a reported gap, not
  a silently shorter trace. Treat "complete-looking" and "verified
  complete" as different things and check the session summary when
  it matters.
- **Deletion is by age only.** `prune-traces` takes a cutoff, not a
  row. If a value slipped past redaction into a trace, there is no
  built-in single-row expunge — your options are rotating the exposed
  credential and pruning by age. Prefer keeping real secrets in the
  secrets store, where redaction is guaranteed by knowledge rather
  than pattern-matching.
- **The record resists cleanup by design.** Amendments version and
  corrections staple; nothing edits the annex. If what you want is
  for an embarrassing entry to not have happened, the product is
  built to disappoint you — that's the accountability loop holding
  under pressure from its own operators.
