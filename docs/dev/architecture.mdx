# Architecture

csuite is a command-and-control plane for AI agent teams. A
**broker** is authoritative about a team's state — context,
members, objectives, channels, captured activity. A **runner**
(`csuite claude` or `csuite codex`) wraps an agent's CLI in a
parent process that talks to the broker and relays push events
into the agent's session. The agent itself runs as a child of the
runner.

```
   member terminal
        │
        ▼
   ┌─────────────────────────┐
   │   csuite <runner verb>     │
   │                         │
   │   ── runner, long-lived ──
   │   • broker Client       │   <── HTTP + WebSocket
   │   • instructions cached │
   │   • IPC server (UDS)    │
   │   • capture host (native)
   │   • objectives tracker  │
   │   • busy reporter       │
   │   • event forwarder     │
   │                         │
   │   spawns ↓              │
   └────────┬────────────────┘
            │ OTEL export env (claude)
            │ CSUITE_RUNNER_SOCKET=...
            ▼
   ┌─────────────────────────┐
   │   the agent             │
   │   (claude / codex / ...) │
   └───┬──────────────┬──────┘
       │              │ stdio MCP (claude)
       │ native       │ stdio JSON-RPC (codex)
       │ instrument-  ▼
       │ ation    ┌─────────────────────────┐
       │          │   csuite mcp-bridge        │  (claude only)
       │          └────────┬────────────────┘
       │                   │ IPC frames over UDS
       │                   ▼
       │              back to the runner
       ▼
   claude → session transcript + OTEL → readers → broker
   codex  → rollout JSONL + OTEL + trace bundles → readers → broker
```

Why this shape: the runner is **upstream** of the agent. That's
what lets it inject each agent's native-instrumentation config
(the OpenTelemetry export env for claude), pass adapter configuration
without rewriting operator files, and own the loopback hook server
and activity uploader. A bridge running as a child of the agent —
the older shape — couldn't do any of that.

## Three credential paths, one member identity

The broker accepts three credential paths:

```
        ┌─ humans ─┐       ┌─ runners ─────────┐       ┌─ federation ─┐
        │ browser  │       │ csuite claude   │       │ RS256 JWT    │
        └────┬─────┘       │ csuite codex         │       └───────┬──────┘
             │ session     └─────────┬─────────┘               │ bearer
             │ cookie                │ opaque bearer           │ token
             ▼                       ▼                         ▼
                  ╔═══════════════════════════════════════╗
                  ║    csuite-web-host (PWA)  +  REST API    ║
                  ║         csuite-server               ║
                  ║         csuite-core                 ║
                  ╚═══════════════════════════════════════╝
```

All three pass through the same auth middleware and resolve to a
loaded member. Federated JWT support is optional. Downstream
handlers act on the resolved member and their **permissions**,
not on which accepted credential path authenticated them.

For the full enrollment flow (RFC 8628 device-code, multi-token,
TOTP rotation) see [device enrollment](/docs/enrollment).

## The runner abstraction

csuite ships with two runners and is designed for more. Both share
all the broker-facing plumbing — auth, instructions, IPC server,
event forwarder, MCP tool dispatch, capture host, busy reporter, and
the drain-and-restart coordinator that applies instruction edits by
restarting the agent at its next idle boundary — and their principal
adapter-specific differences are:

1. **How the agent is spawned.** Claude Code runs headlessly under
   the Claude Agent SDK; codex is headless under `codex app-server`.
2. **How broker events reach the agent.** Claude: an Agent SDK
   streaming-input user message. Codex: a `turn/start` (idle) or
   `turn/steer` (active) JSON-RPC dispatch. Both bundle bursts
   within a 200ms window and share the `<channel>` rendering.
3. **How native instrumentation is captured.** Claude content is
   transcript-primary: the runner tails the session transcript,
   hooks provide lifecycle presence and the transcript path, and
   OpenTelemetry remains a lean operational signal. Codex content
   comes from rollout files and persisted bundles; the app-server
   stream provides lifecycle, busy-state, and injected-input control.

The runner core (`startRunner` in
`packages/cli/src/runtime/runner.ts`) accepts a
`channelSink` option through which each adapter defines how
broker events are delivered. Everything else is shared.

For the per-runner reference see
[runners overview](/docs/runners/overview),
[runners/claude](/docs/runners/claude), and
[runners/codex](/docs/runners/codex).

## Permission model

csuite has no fixed director / manager / individual-contributor hierarchy. Every
member resolves to a flat set of leaf permissions. Elevated actions
gate on a specific leaf or on an explicitly documented relationship
bypass such as self or objective originator:

| Permission | What it permits |
|---|---|
| `team.manage` | Edit team name / context / presets |
| `members.manage` | Create / update / delete members; rotate any token |
| `objectives.manage` | Direct the team's work: create + assign, cancel any non-terminal (originator-bypass), reassign, manage watchers (originator-bypass) |
| `activity.read` | View captured traces (self-bypass) |
| `tools.manage` | Administer the tool-source registry (external tools) |
| `secrets.manage` | Administer the secrets registry (env secrets for agents) |
| `notifications.manage` | Administer inbound notification endpoints and delivery policy |
| `process.manage` | Edit the team's process document (a dedicated leaf) |

The team config defines named **presets** (e.g. `admin`,
`operator`) that members reference instead of listing every leaf.
The server resolves presets at config load time; what reaches the
wire is always the flat list.

For the full breakdown see [permissions](/docs/concepts/permissions).

## The runner / bridge process tree (claude)

```
   ┌──────────────────────────────────┐
   │   csuite claude                │
   │                                  │
   │   ── runner (parent) ──          │
   │   • instructions + objectives    │
   │   • event forwarder              │
   │   • CaptureHost (hook server,    │
   │     loopback OTLP relay, and     │
   │     activity uploader live here) │
   │   • IPC server on UDS            │
   │                                  │
   └──────────────┬───────────────────┘
                  │ exec claude with
                  │   CLAUDE_CODE_ENABLE_TELEMETRY=1
                  │   OTEL_EXPORTER_OTLP_ENDPOINT=http://127.0.0.1:<relay>/otlp
                  │   OTEL_EXPORTER_OTLP_HEADERS=Authorization=Bearer …
                  │   OTEL_LOG_RAW_API_BODIES=file:<runner spool dir>
                  │   prose telemetry disabled
                  │   CSUITE_RUNNER_SOCKET=/tmp/.csuite-runner-$PID.sock
                  ▼
   ┌──────────────────────────────────┐
   │         claude (CLI)             │
   │                                  │
   │ receives bridge config inline    │
   │ from the Agent SDK options       │
   │ (the user's .mcp.json is intact) │
   │ exports OTLP → runner relay,     │
   │   which forwards to broker /otlp │
   │ POSTs hook events → hook server  │
   └──────────────┬───────────────────┘
                  │ stdio JSON-RPC (MCP)
                  ▼
   ┌──────────────────────────────────┐
   │   csuite mcp-bridge                 │
   │                                  │
   │   ── thin relay, no state ──     │
   │   • connects to runner's UDS     │
   │   • wraps every MCP request as   │
   │     `mcp_request` frame          │
   │   • emits every runner-initiated │
   │     `mcp_notification` frame as  │
   │     a real MCP notification      │
   │                                  │
   └──────────────┬───────────────────┘
                  │ IPC frames (newline JSON)
                  ▼
          back to the runner
```

The codex shape is similar — codex gets its config via an ephemeral
CODEX_HOME instead of the SDK's inline MCP config, and its channel
sink dispatches `turn/start`/`turn/steer` JSON-RPC instead of
streaming-input messages.

For the wire format of those IPC frames, see
[ipc-protocol](/docs/dev/ipc-protocol).

## Concepts at a glance

| Concept | One-line summary | Doc |
|---|---|---|
| **Member** | A named seat on a team. Identity = name + role + permissions + bearer token(s). | [members](/docs/concepts/members) |
| **Permissions** | Eleven leaf permissions; preset bundles; originator + self bypass rules. | [permissions](/docs/concepts/permissions) |
| **Objective** | Push-assigned, single-assignee, outcome-required, four-state work primitive with audit log + threaded discussion + attachments. | [objectives](/docs/concepts/objectives) |
| **Channel** | Slack-style named team thread. Implicit `general` + named channels with admin/member roles. | [channels](/docs/concepts/channels) |
| **Event / message** | Push-not-poll delivery. Routes by `data.thread`. Wraps as `<channel>` for the agent. | [events](/docs/concepts/events) |
| **Presence** | "On the wire" via the WebSocket subscriber registry; "currently working" via runner heartbeats with TTL. | [presence](/docs/concepts/presence) |
| **Activity / traces** | Append-oriented timeline per member with explicit pruning; per-objective trace = time-range slice. | [activity-and-traces](/docs/concepts/activity-and-traces) |

## How a chat push flows end-to-end

1. Member runs `csuite push --agent scout --body "ci failed"` (or
   `POST /push` directly, or clicks send in the web UI).
2. Broker validates against `csuite-sdk/schemas`, writes to the
   event log, and fans out to every recipient based on
   `data.thread`. For a DM, `to: 'scout'` resolves to scout's
   subscribers.
3. Scout's runner holds a WebSocket subscription on
   `/subscribe?name=scout`. The forwarder receives the frame,
   suppresses self-echoes, and delivers a typed channel event to the
   adapter's channel sink.
4. **claude path:** sink renders the `<channel>`-tagged prose and
   injects it as an Agent SDK streaming-input user message (queued
   natively if the agent is mid-turn).
5. **codex path:** sink buffers (200ms window), then dispatches
   `turn/start` (if idle) or `turn/steer` (if active mid-turn) on
   the JSON-RPC channel. Codex receives a UserInput item carrying
   the same `<channel>`-tagged prose.
6. The model wakes and reacts. No human prompt, no polling.

The machine delivery plane is HTTP → broker → WebSocket → runner →
the adapter's native input channel (Claude Agent SDK streaming
input or codex app-server JSON-RPC) → model. The MCP bridge is
the tool-call path for Claude, not the channel-delivery path.
There is also a parallel
HTTP → broker → web-push library → push service → service worker
→ OS notification shell for humans.

## How an objective flows

1. A member with `objectives.manage` calls `objectives_create`
   (MCP tool) or runs `csuite objectives create`.
2. The store inserts the row, appends an `assigned` audit event
   in the same transaction, and the app layer publishes an
   objective channel event to the thread members (originator,
   assignee, watchers).
3. The assignee's runner sees the event on its subscription; the
   objectives tracker refreshes its open-plate snapshot — the seed for the
   `context_refresh` push the runner sends at session attach
   and after context compaction. (Tool descriptions stay static so
   the model's prompt-prefix cache survives; state freshness is
   message traffic.)
4. When the runner's refreshed open-objective set gains or loses an
   id, it enqueues an `objective_open` or `objective_close` marker.
   It also records open markers for objectives present when a runner
   starts. These markers describe what that runner observed; the
   objective audit log remains authoritative for lifecycle state.
   Claude transcript capture or codex rollout capture flows through
   the activity uploader as `llm_exchange`, `tool_action`, and
   `user_prompt` events.
5. The agent works: posts discussion via `objectives_discuss`,
   transitions blocked / active via `objectives_update`, and
   eventually calls `objectives_complete` with a required result.
6. On a terminal transition (or reassignment away), the tracker
   refreshes and the runner enqueues an `objective_close` marker.
   The uploader batches events and posts them while the runner is
   live; its bounded queue reports any drops under sustained broker
   unreachability.
7. A director (or anyone with `activity.read`) opens the objective
   in the web UI. The TracePanel queries
   paged activity and gen_ai queries over the objective's
   `createdAt` through `completedAt` (or the current time when there
   is no completion timestamp). Access requires self or
   `activity.read`. The panel joins activity markers to full-context
   inference records and reports when that enrichment is unavailable.

### Components

| Package | Role | Install when you want |
|---|---|---|
| **`csuite`** | Meta-package. Installs the CLI, server, SDK, and core; no code of its own. | The command and broker stack in one install |
| **`csuite-sdk`** | The wire contract. Types, zod schemas, protocol constants, TS client. Everything speaks this. | To embed a client in your own Node / Workers / browser code |
| **`csuite-core`** | Runtime-agnostic broker logic: registry, push fanout, event/session/push stores, and trace transforms; depends on `csuite-sdk` for the shared contract. HTTP authentication and route permission checks live in the server. | To build a custom broker runtime |
| **`csuite-server`** | Node broker. Wraps `core` in Hono + `node:sqlite`. Team config loader, first-run wizard, objectives + activity persistence, virtual filesystem, web push, optional JWT federation, built-in web UI. | To host a self-hosted broker |
| **`csuite-web-ui`** | Published, host-agnostic Preact team-view UI + runtime — chat, objectives (with TracePanel), files, members, tools, secrets, roster, live subscription. Distributed as source and exposes `<TeamShell>`. | To embed the shared UI in another host |
| **`csuite-web-host`** | Published reference web host: TOTP auth gate + PWA that mounts `csuite-web-ui`'s `<TeamShell>`. Its built assets also ship inside `csuite-server`. | To run or customize the standalone reference host |
| **`csuite-cli`** | Member terminal. `csuite claude`, `csuite codex`, `csuite push`, `csuite roster`, `csuite objectives`, `csuite serve`, etc. Also hosts the internal `csuite mcp-bridge` verb. | To push / inspect from a terminal or run a runner |

**Light install:** `csuite-cli` does not hard-depend on
`csuite-server`; the server is an optional peer and server-backed
subcommands dynamically import it with an install hint when it is
missing. The CLI itself also depends on `csuite-core`,
`csuite-sdk`, the Claude Agent SDK, and the MCP SDK.

## Trace capture

The runner maintains one append-oriented **activity stream** per
member, fed by each agent's **native instrumentation** — Claude
Code's session transcript, hooks, and OTEL export (through a
runner-local loopback relay that inlines file-mode raw bodies);
codex's rollout JSONL, OTEL export, and trace bundles — plus
runner-observed objective-open/close markers. There is no network
interception, no TLS decryption, and no CA on disk. Per-objective
"traces" are a time-range view over the stream; no per-objective
blobs are stored anywhere.

The full pipeline — the capture host, transcript and rollout
readers, the OTLP relay, broker-side correlation, redaction
boundaries, and uploader queue accounting — lives at
[trace-pipeline](/docs/dev/trace-pipeline). For the data model see
[activity-and-traces](/docs/concepts/activity-and-traces).

## Transport

- **HTTP/2** when HTTPS is active. Removes the browser
  6-connection-per-origin cap on long-lived HTTP/1.1 requests so
  multi-tab users don't deadlock.
- **HTTP/1.1** fallback via ALPN for legacy clients. Same
  listener, same cert.
- **Self-signed certs** auto-generated on first boot when binding
  to a non-loopback interface. Stored under the config directory
  at `0o600`; the server can hot-reload a supplied certificate via
  `SecureContext` swap.

## Protocol versioning

The SDK adds `X-CSUITE-Protocol: 2` to its HTTP and subscription
requests (v2 renamed the composed-context surface to
`GET /instructions` and added instruction-block versioning). The
broker allows clients that omit it, but rejects a
present incompatible version with 400. Request and response shapes
are validated at typed SDK/server boundaries with the zod schemas
in `csuite-sdk/schemas`. Breaking wire changes require a protocol
version bump; the current code does not itself guarantee
cross-version compatibility beyond rejecting an explicitly
incompatible header.
