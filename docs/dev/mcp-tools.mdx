# MCP tools reference

This reference is for people building on the runner's MCP surface or
contributing to it — the user-facing story lives in the concepts
pages.

The csuite runner exposes a fixed toolbox to whatever agent it
spawns. Tool descriptions are composed from the instructions packet
at runtime (the member's fs home path, permission-scoped wording) so
what the model sees is stable for the session.

The groups:

- **Chat tools** — message teammates, post to channels, fetch
  history.
- **Objective tools** — list / view / update / discuss / complete
  objectives, plus permission-gated tools for authoring, amending,
  and correcting objectives created by others.
- **Process-document tools** — read the team's process document and
  its edit history; write it if you hold the authority. The current
  text arrives by injection, not by calling these.
- **Spine tools** — the team's append-only annex and the contracts
  folded out of it: orient, read, author, attempt, judge, complete,
  ask, rule, proceed, observe, discuss, promote. Two are gated on
  `spine.author`; the rest are baseline participation.
- **Filesystem tools** — operate on the csuite virtual filesystem
  under the agent's own home (`/<name>/`).
- **Admin tools** — permission-gated groups for team config and
  presets (`team.manage`), member management (`members.manage`),
  tool sources (`tools.manage`), secrets and variables
  (`secrets.manage`), and external notifications
  (`notifications.manage`).
- **External tools** — resolved per member from the tool-source
  registry, namespaced `<source>__<name>`.

All schemas below use the JSON Schema fragment the runner emits
through `tools/list`. Strings are JS strings, numbers are JS
numbers, arrays are JS arrays.

## Chat tools

### roster

List teammates with role, authority, connection state, and recent
activity.

| | |
|---|---|
| **Input** | `{}` |
| **Output** | Text block: `team <name> roster:` followed by per-line `- <name> (you)? [<role>] [admin\|operator]? connected=N\|offline; activity=<reported working\|blocked …\|no report …>` (activity is qualified by the broker's reporting window) |
| **Broker call** | `GET /roster` |

### broadcast

Post a message to the team's `general` channel. Every teammate sees
it immediately on their live stream.

| | |
|---|---|
| **Input** | `{ body: string (req, ≤ 65536 chars), level?: LogLevel, attachments?: string[] (≤ 64) }` |
| **Output** | `broadcast delivered: live=N targets=M msg=<id>` |
| **Broker call** | `POST /push` with `to: null` |

`attachments` are virtual filesystem paths (e.g.
`/<name>/uploads/report.pdf`). Each must already exist and be
readable to the caller; the runner resolves each via `fs_stat`
before posting and rejects with `attachment not found: <path>` on
the first miss. Recipients automatically receive read access to
each attached path via the resulting message.

`level` is one of `debug | info | notice | warning | error |
critical`; defaults to `info`.

### send

DM a specific teammate by name. Private to caller and target.

| | |
|---|---|
| **Input** | `{ to: string (req), body: string (req, ≤ 65536 chars), level?: LogLevel, attachments?: string[] (≤ 64) }` |
| **Output** | `delivered to <to>: live=N targets=M msg=<id>` |
| **Broker call** | `POST /push` with `to: <name>` |

Same attachment rules as `broadcast`; the recipient receives read
access.

### channels_list

List named channels the caller has access to. `general` is always
included (implicit membership). Joined channels are listed first,
then visible-but-not-joined.

| | |
|---|---|
| **Input** | `{}` |
| **Output** | Text: `channels you belong to:` + entries like `- #frontend [admin] members=4` |
| **Broker call** | `GET /channels` |

### channels_post

Post a message into a specific channel. The caller must be a
member of that channel; non-members get
`channels_post: you are not a member of #<slug>...`.

| | |
|---|---|
| **Input** | `{ channel: string (req, slug), body: string (req, ≤ 65536 chars), level?: LogLevel, attachments?: string[] (≤ 64) }` |
| **Output** | `posted to #<slug>: live=N targets=M msg=<id>` |
| **Broker call** | `GET /channels/:slug` to resolve id, then `POST /push` with `data: { thread: 'chan:<id>' }` |

The channel is addressed by slug (mutable, URL-facing), but the
runner resolves slug → id and pins `data.thread = 'chan:<id>'` on
the push so a rename never orphans the message. Channel members
receive read grants for each attached path.

### recent

Fetch recent messages from one of three scopes: the general team
channel (default), a DM thread with one teammate, or a named
channel. Pass `with` xor `channel`.

| | |
|---|---|
| **Input** | `{ with?: string, channel?: string, limit?: number }` |
| **Output** | Header line + per-message lines: `<ts> <from> → <to>? [<title>?]: <body>` |
| **Broker call** | `GET /channels/:slug` (if `channel`) then `GET /history?...` |

`limit` defaults to 50, capped at 500. Newest-first ordering.

## Objective tools (always available)

### objectives_list

List objectives the caller has a relationship with — assigned to
them, originated by them, or watched. `status: 'open'` is the
active+blocked union (the whole open plate in one call — what
recovery after a restart or compaction wants); the unfiltered call
also returns full done/cancelled history. Use `objectives_view`
for the watcher list and audit log.

| | |
|---|---|
| **Input** | `{ status?: 'active' \| 'blocked' \| 'done' \| 'cancelled' \| 'open', assignee?: string }` |
| **Output** | Per-objective: `- <id> [<status>] <title>` + assignee/originator + outcome line + relative-age update line |
| **Broker call** | `GET /objectives?status=<filter>&assignee=<filter>` (the broker scopes non-`objectives.create` callers to their own relationship union) |

### objectives_view

Full state for a single objective: title, outcome, status,
assignee, originator, watchers, body, blockReason, result, plus
the append-only `objective_events` audit log.

| | |
|---|---|
| **Input** | `{ id: string (req) }` |
| **Output** | Multi-line block with all fields + `events:` followed by `<ts> (<age>) <actor> <kind> <payload>` per event |
| **Broker call** | `GET /objectives/:id` |

### objectives_update

Transition status (`active ↔ blocked`) and/or post a block reason.
**This tool only handles state transitions** — for progress notes
or questions use `objectives_discuss`. For terminal `done` use
`objectives_complete`. For `cancelled` use `objectives_cancel`
(if you have permission).

| | |
|---|---|
| **Input** | `{ id: string (req), status: 'active' \| 'blocked' (req), blockReason?: string (required when status=blocked) }` |
| **Output** | `updated <id>: status=<status> blockReason="<reason>"?` |
| **Broker call** | `PATCH /objectives/:id` |

### objectives_discuss

Post a discussion message into the `obj:<id>` thread. Thread
members (originator, assignee, watchers, plus members with
`members.manage` as implicit observers) all receive it on their
live streams.

| | |
|---|---|
| **Input** | `{ id: string (req), body: string (req, ≤ 16384 chars), attachments?: string[] (≤ 64) }` |
| **Output** | `posted to objective <id> thread: msg=<id> attachments=N? (fanned out to thread members)` |
| **Broker call** | `POST /objectives/:id/discuss` |

### objectives_complete

Mark an objective `done` with a required result string. Only the
current assignee can call this. The result becomes part of the
audit log.

| | |
|---|---|
| **Input** | `{ id: string (req), result: string (req) }` |
| **Output** | `completed <id>. Result recorded and originator notified.` |
| **Broker call** | `POST /objectives/:id/complete` |

## Objective tools (permission-gated)

The runner only adds these to the tool list when the caller's
permissions allow them. The server enforces the same rules
independently — a stale MCP client name-calling a hidden tool
gets a 403 from the broker.

Note on the toolbox gate as registered today: the whole group
surfaces only when the caller holds `objectives.create`
(`buildAuthorityTools` returns early without it). The
originator-bypass on `objectives_cancel` / `objectives_watchers`
below is the **server's** rule — the broker honors it on the HTTP
API regardless of what the toolbox shows — and the tool
descriptions adapt their scope wording when the caller lacks the
broader permission.

### objectives_create

Create and assign a new objective. Available when caller has
`objectives.create`. The originator is stamped as the caller.

| | |
|---|---|
| **Required permission** | `objectives.create` |
| **Input** | `{ title: string (req), outcome: string (req), assignee: string (req), body?: string, watchers?: string[], attachments?: string[] }` |
| **Output** | `created <id> assigned to <name>: <title>` + outcome + watchers + attachments lines |
| **Broker call** | `POST /objectives` |

The `outcome` field is contractual: it must state the tangible
verifiable result, not just intent. The runner re-checks the
permission locally for a faster error message; the server is the
authoritative gate.

### objectives_amend

Amend an objective's contract — outcome, title and/or body. The
gate is the permission, not the role: an assignee holding
`objectives.create` may amend their own contract. Prior text is
kept and rendered by `objectives_view`; a no-op amendment (no field
differs) is rejected rather than recorded as a version bump.
`disposition` is required: `correction` is retroactive (the prior
text was wrong), `scope_change` is forward-only (work already
underway finishes under the prior text).

| | |
|---|---|
| **Required permission** | `objectives.create` |
| **Input** | `{ id: string (req), outcome?: string, title?: string, body?: string, reason: string (req), disposition: 'correction' \| 'scope_change' (req) }` |
| **Output** | `amended '<id>' to contract version <N> (<disposition>: <what it binds>). The prior text is kept and shown by objectives_view.` |
| **Broker call** | `POST /objectives/:id/amend` |

### objectives_correct_event

Correct an earlier lifecycle event — most often a completion
recorded at the wrong moment. The original event is never
rewritten: this appends a superseding record naming it, and
`objectives_view` marks the corrected event inline. Does not bump
the contract version. `eventId` comes from the event log in
`objectives_view` (a timestamp is not an identity — creation emits
two events in the same millisecond).

| | |
|---|---|
| **Required permission** | `objectives.create` |
| **Input** | `{ id: string (req), eventId: string (req), correction: string (req), reason: string (req) }` |
| **Output** | `recorded a correction on '<id>'. The original event is unchanged and is now marked corrected in objectives_view.` |
| **Broker call** | `POST /objectives/:id/correct-event` |

### objectives_cancel

Terminally cancel an objective. Available when caller has
`objectives.cancel`, OR is the originator (originators can always
cancel their own). Cancellation is terminal — create a fresh
objective if priorities change again.

| | |
|---|---|
| **Required permission** | `objectives.cancel` (originator-bypass) |
| **Input** | `{ id: string (req), reason?: string }` |
| **Output** | `cancelled <id>: <title>` |
| **Broker call** | `POST /objectives/:id/cancel` |

### objectives_watchers

Add or remove watchers on an objective's discussion thread.
Watchers receive every lifecycle event and every discussion post
without being the assignee. Available when caller has
`objectives.watch`, OR is the originator.

| | |
|---|---|
| **Required permission** | `objectives.watch` (originator-bypass) |
| **Input** | `{ id: string (req), add?: string[] (≤ 64), remove?: string[] (≤ 64) }` (must include at least one) |
| **Output** | `updated <id> watchers: <name1>, <name2>...` |
| **Broker call** | `POST /objectives/:id/watchers` |

### objectives_reassign

Reassign a non-terminal objective to a different teammate.
Available only when caller has `objectives.reassign`.

| | |
|---|---|
| **Required permission** | `objectives.reassign` |
| **Input** | `{ id: string (req), to: string (req), note?: string }` |
| **Output** | `reassigned <id> to <new>: <title>` |
| **Broker call** | `POST /objectives/:id/reassign` |

Both old and new assignees receive channel pushes. The previous
assignee's activity stream gets an `objective_close` and the new
assignee's gets a fresh `objective_open`, so the trace time-range
shifts cleanly.

## Process-document tools

The team's process document is **injected**: the current text is
already in the agent's fixed context as current state, and it survives
compaction. An agent does not call a tool to learn what binds it.

### process_document_get

| | |
|---|---|
| **Required permission** | none |
| **Input** | `{}` |
| **Output** | `process document v<N>, last edited by <name>. Created by <name>.` then the text; or an explicit "no process document has been set" |
| **Broker call** | `GET /process-document` |

Returns a real state rather than an error when none has been set —
`null` means nobody has written one, not that you cannot see it.

### process_document_history

| | |
|---|---|
| **Required permission** | none |
| **Input** | `{}` |
| **Output** | Per edit: version, actor, `disposition` and what it binds, reason, and whether prior text exists |
| **Broker call** | `GET /process-document/history` |

The other half of *history retrievable, not resident*: the injected
context carries only current text, so editing fifty times costs what
editing once costs. Version 1 is the creation and carries no prior
text.

## Process-document tools (permission-gated)

### process_document_write

| | |
|---|---|
| **Required permission** | `process.manage` |
| **Input** | `{ text: string (req), reason: string (req), disposition: 'correction'\|'scope_change' (req) }` |
| **Output** | `created`/`updated the process document at v<N>` + what the disposition binds + the delivery bound |
| **Broker call** | `PUT /process-document` |

**`text` REPLACES the whole document.** Read it with
`process_document_get` and send the full new text — this is not a patch
API, and sending a paragraph deletes everything you did not retype.

The first write creates version 1; every later write increments the
version and retains the prior text, so nothing is destroyed.

`disposition` is the same field with the same meaning as
`objectives_amend`, so *does work started under the old process finish
under it* has one answer across contracts and process.

### Delivery bound

An edit fans out one `kind: 'instructions'` broker event to every
member whose composed context changed. Each affected runner restarts
its agent at the next idle boundary, resuming the same conversation
under the new text, and `GET /roster` lists those members in
`restartPending` until it does. The `#103` context watchdog keeps
the document in place mid-session: if it falls out of context
entirely, an observable turn detects the absence and re-sends it.

Its membership test differs from the authored blocks' and has to.
Those are confirmed by substring against the composed `instructions`;
this is never in that string, so its test is that it was **sent**, and
the bytes projected are the document's own.

An agent still holding a superseded version reads as **stale**, not
missing — it is restart-pending, never re-sent content, because
injecting the new text beside the old would put two versions in one
context.

**Codex members are the partial exception**: a codex-uploaded
inference is treated as observable only when it carries a non-empty
system projection. When the projection is empty, absence cannot be
asserted and nothing is re-sent.

A runner predating the field drops it silently: the member operates
without the process document and is not told.

## Spine tools

The spine is the team's durable record — one append-only annex of
captioned events, the subjects those events are about, and the
contracts folded out of them. See
[the REST surface](/docs/dev/rest-api#spine) for the endpoints these
tools call and the refusal payloads they render.

Two properties shape this whole group and neither is cosmetic:

**The schemas are the law.** A required field is the one lever that an
agent cannot route around, so every caption that would silently lie by
being absent is required — `expected_state_rev` on writes that change
what the team owes, a whole `{value, how, source}` revision wherever a
value is claimed, `why` on a `cannot_verify` verdict, `unblocks` on an
ask nobody could otherwise price.

**The refusals are the product.** A stale write returns every
authoritative event the caller missed, rendered event by event with
captions and whole bodies; a coverage gap returns every uncovered
criterion and why; the citation lock returns the ask itself. None of it
is capped or summarised — the refusal is the re-injection, delivered at
the moment stale beliefs would have caused harm.

### The citation lock

While a member has an unresolved `ask` on a subject — **or on any
subject containing it** — the annex refuses their state-changing acts
there until either the ask is answered or they record a `proceed` past
it. The locked acts are `contract_author`, `contract_amend`,
`attempt_post`, `verdict_post`, `state_set` and `contract_complete`.

The refusal states the absence flatly: *YOU DO NOT HAVE A RULING ON
IT*. That wording is the feature. The failure being closed is a member
acting on authorisation they remember receiving, and a phrasing like
"cite a ruling" reads as a formality to someone who believes they have
one.

**Getting the ruling is itself the release.** A ruling resolves its
ask, and a resolved ask locks nothing, so there is no citation left to
perform afterwards — §5's "must cite a `ruling` id" describes a state
the annex reaches by resolution rather than a step the member takes.
(The store still accepts a cited ruling as cover, for the day an ask
outlives a ruling that only partly answered it; today no input can
reach that branch.)

An ask binds only as far as it is **scoped**: by its `subject`, or —
when it names only a `contract` — by that contract's subject. An ask
carrying neither scopes nothing and binds nothing, and `ask_author`
says so in its result rather than promising a lock the member does not
get.

It binds the **asker**, never the authority — a lock that spread the
other way would make asking someone a way to stop them working. One
`proceed` covers that actor until that ask resolves; a *different* open
ask needs its own. `discuss`, `observe`, `testimony`, and the lock's
own exits (`ask_author`, `ruling_post`, `proceed`) are never locked.

**A redirect does not release anyone.** Re-addressing a question is not
answering it, so `ask_action: redirect` leaves the ask **open** with a
new `authority` — one durable ask, one id, the move recorded by the
`ask_action` event. The asker stays locked, the new authority may rule,
the old one may not, and a redirect back to the asker is refused for
the same reason an ask may not name its own asker as authority.

**A contract-bound act is about its contract's subject.** An
*authoritative* event naming a contract may caption itself with that
contract's subject or anything contained in it; a caption pointing
elsewhere is refused with `invalid_input` naming both. Without that
rule, `subject` — optional on four of the five locked kinds and
settable through `promote` — moved the act into a scope where the actor
had no asks, and the lock passed it.

Ambient kinds are exempt, deliberately. The rule exists to protect the
lock, the lock never touches an ambient kind, and a post is a remark
about the world rather than an act on it — *"aside: repo:other has the
same bug"* on a thread about this contract must stay free to write, or
the conversation gets expensive and the annex stops measuring what §14
measures.

### orient

The recovery call. No arguments, no preconditions, and it cannot be
refused.

| | |
|---|---|
| **Required permission** | none |
| **Input** | `{}` |
| **Output** | Per bound contract: id, title, state, `state_rev`, how you are bound, subject, the bound revision whole, a staleness line naming both revisions, every criterion with its verdict and the revision it was reached at, and the rulings that bind it. Then asks awaiting your ruling, your own open asks, and the annex cursor. |
| **Broker call** | `GET /spine/orient` |

Call it after any restart, compaction or gap. Guessing costs more than
the call, and that sentence is in the description because the moment it
is needed most is the moment there is least context left to read with.

An empty pack renders as *"No contracts bind you right now"* — a real
state, not an empty read.

### annex_read

| | |
|---|---|
| **Required permission** | none |
| **Input** | `{ since_seq?: number, limit?: number (1–500), kind?: string, subject?: string, contract?: string, actor?: string }` |
| **Output** | Each event with its captions and whole body, oldest first, then the next cursor |
| **Broker call** | `GET /spine/events` |

`subject` resolves containment — a repo returns the files inside it.
`next_cursor` is null **only** when the page reached the head; an empty
page with a cursor means "nothing new yet", which is a different claim.

### attempt_post

| | |
|---|---|
| **Required permission** | none |
| **Input** | `{ contract, summary, revision: {value, how, source, subject?}, expected_state_rev, op_id? }` |
| **Output** | The event id, and where the contract now stands |
| **Broker call** | `POST /spine/events` (kind `attempt`) |

The readiness signal: it binds the contract to a revision and lights
the verifier's `orient`. The revision's `subject` defaults to the
contract's own.

### verdict_post

| | |
|---|---|
| **Required permission** | none |
| **Input** | `{ contract, criterion, decision: 'met'\|'unmet'\|'cannot_verify', evidence, why?, revision, expected_state_rev, op_id? }` |
| **Output** | The decision, criterion and revision, and where the contract now stands |
| **Broker call** | `POST /spine/events` (kind `criterion_verdict`) |

One criterion at a time — partial is the native shape. A verdict from
the contract's **assignee** is refused by the annex whatever
permissions the caller holds: arrival cannot be declared from the
traveller's own album. `cannot_verify` requires `why`, and the tool
refuses without one before spending a round trip.

### state_set

| | |
|---|---|
| **Required permission** | none |
| **Input** | `{ contract, state: 'active'\|'waiting_on'\|'waiting_for'\|'parked'\|'cancelled'\|'superseded', expected_state_rev, reason?, member?, event?, check?, preempted_by?, successor?, op_id? }` |
| **Output** | The new state, and the counter to use next |
| **Broker call** | `POST /spine/events` (kind `lifecycle`) |

`done` is refused here and points at `contract_complete`: there is
deliberately no second route to done that skips the evidence check.
`waiting_for` carries the event **and** the check that will re-light
it — without a check the contract goes silent with nothing able to wake
it.

`check` may be prose, or it may be a **probe recipe** (see below). A
recipe re-lights the contract by itself: when it fires, an observation
lands and the contract goes back to `active` citing it, with nobody
nagged and no human in the loop.

### contract_complete

| | |
|---|---|
| **Required permission** | none |
| **Input** | `{ contract, result, revision, cites: string[], expected_state_rev, op_id? }` |
| **Output** | The completion, and the contract's terminal state |
| **Broker call** | `POST /spine/events` (kind `lifecycle`, state `done`) |

The one hard gate besides the citation lock. With a verifier named,
cited verdicts (or rulings waiving a `cannot_verify`) must cover every
criterion at one revision; the refusal names each criterion that is not
covered and why, which is the shortest description of what is left to
do. With no verifier, the result stands alone and the record says so.

### ask_author

| | |
|---|---|
| **Required permission** | none |
| **Input** | `{ authority, question, context, unblocks, subject?, contract?, expected_state_rev?, trigger?, check?, op_id? }` |
| **Output** | The ask id, and a restatement that raising it has bound the asker |
| **Broker call** | `POST /spine/events` (kind `ask`) |

`context` and `unblocks` are required because an ask nobody can price
is an ask nobody answers. The authority cannot be the caller. Naming a
`contract` makes it a state-changing write on that contract and
requires `expected_state_rev`; omitting the contract refuses one.

`check` may be prose, or a **probe recipe** (below). With a recipe, the
ask can be answered by the world rather than by the authority: when it
fires, the ask closes as `discharged` with the observation stapled to
it and the asker gets one line. The authority does the thing and types
nothing.

### Probe recipes — arming a check

There is no `check_author` tool, deliberately: a check is authored
inside the thing it discharges, so it cannot outlive its reason and
withdrawing that reason takes it along. The `check` field on
`ask_author` and `state_set` (and `trigger` on a deferring
`ask_action`) accepts either prose — which arms nothing and is refused
by nothing — or a JSON recipe, recognised by a leading `{`.

```json
{"kind":"webhook","endpoint":"ci",
 "when":[{"path":"check_run.conclusion","op":"eq","value":"success"}],
 "revisionPath":"check_run.head_sha"}
```

```json
{"kind":"http_poll","url":"https://ci.example.com/status","intervalMs":300000,
 "when":[{"path":"state","op":"eq","value":"green"}],"authSecret":"ci-token"}
```

`when` is the inbound-notification filter rule set (`eq`, `ne`, `in`,
`exists`, `contains`; an empty list matches any delivery) — the same
engine the webhook inbox evaluates, not a second dialect.
`revisionPath` names a value that IS an observation point and rides in
as an *observed* revision.

The observation a firing check produces carries `actor:
probe:<check-id>` and `authored_by: <you>`: **you composed the shot,
the system held the camera.** It fires once — re-arming takes a new ask
or a fresh `waiting_for` — and a predicate that says no produces
nothing at all.

`http_poll` is refused at authoring unless it is `https://`, its
interval is at least 60000ms, any credential is named by secret **slug**
rather than written out, and the host is not a private, loopback or
link-local address. Redirects are never followed and responses are
size-capped. The slug is resolved server-side as *you*, so a check can
never send a credential you could not have sent by hand.

A **name** is checked again when the poll fires, against every address
it resolves to, and the connection is pinned to those addresses — so
`https://vault.internal/…` is authorable and simply never goes out. A
probe fetches from the server and publishes what it gets to the whole
team; if you genuinely need to poll something internal, an operator
adds the host to the server's allowlist. There is no field on the
recipe that grants it.

### ruling_post

| | |
|---|---|
| **Required permission** | none |
| **Input** | `{ ask, decision, reasoning, contract?, expected_state_rev?, cites?, op_id? }` |
| **Output** | The ruling id and that the ask is resolved |
| **Broker call** | `POST /spine/events` (kind `ruling`) |

Only the ask's named authority may rule; a ruling from anyone else is
not a weaker ruling, it is not a ruling. A ruling citing a
`cannot_verify` verdict **waives** that criterion — the third of the
three legal moves after a verifier says they cannot tell.

### proceed

| | |
|---|---|
| **Required permission** | none |
| **Input** | `{ ask, subject, reason, op_id? }` |
| **Output** | What it covers, and that it is recorded as the actor's own decision |
| **Broker call** | `POST /spine/events` (kind `proceeding`) |

The legal way past your own unresolved ask, and not a workaround: the
annex refuses invented authority, never deliberate action without it.

### observe

| | |
|---|---|
| **Required permission** | none |
| **Input** | `{ subject, what, output, revision? }` |
| **Output** | The event id, plus a note when the revision moved the subject's head |
| **Broker call** | `POST /spine/events` (kind `observation`) |

Ambient: no counter moves and the citation lock never touches it. An
`observed` revision moves the subject's head, which makes contracts
bound to an earlier revision render **stale** — reported, never
repaired.

### discuss

| | |
|---|---|
| **Required permission** | none |
| **Input** | `{ body (max 65536), contract?, subject? }` |
| **Output** | The post id and a reminder that `promote` exists |
| **Broker call** | `POST /spine/events` (kind `discussion`) |

The cheapest surface in the system and the largest cap in it. It
advances no counter, so a busy thread can never veto a lifecycle act,
and it is never refused by the citation lock: the record is expensive
to get wrong and the conversation must never be.

### promote

| | |
|---|---|
| **Required permission** | none (the target kind's own rules still apply) |
| **Input** | `{ event, as, fields?, subject?, revision?, cites?, expected_state_rev?, op_id? }` |
| **Output** | What was promoted, into what, citing the post as origin |
| **Broker call** | `GET /spine/events/:id`, then `POST /spine/events` (kind `as`) |

Turns a discussion post into the typed event it turned out to be. The
post's text becomes that kind's principal field —

| `as` | field the post fills |
|---|---|
| `observation` | `output` |
| `testimony` | `account` |
| `specification` | `title` |
| `amendment` | `changes` |
| `attempt` | `summary` |
| `criterion_verdict` | `evidence` |
| `ruling` | `reasoning` |
| `ask` | `question` |
| `ask_action` / `proceeding` / `lifecycle` | `reason` |
| `correction` | `correction` |

— and anything else that kind requires goes in `fields`, which also
overrides what the post would have supplied. Kinds requiring a contract
(`amendment`, `attempt`, `criterion_verdict`, `lifecycle`) inherit the
post's. The synthesised event **cites the post as its origin**, so the
record shows where the decision actually happened rather than
presenting it as having arrived fully formed. It is a real event of
that kind and is held to every rule that kind carries — promoting is
not a way around a precondition or the citation lock.

Promoting a `discussion` into a `discussion` or a `promotion` is
refused; both are records of records.

### subscribe

| | |
|---|---|
| **Required permission** | none |
| **Input** | `{ contract, level: 'all'\|'lifecycle'\|'none' }` |
| **Output** | The level now in force, and what it does not silence |
| **Broker call** | `PUT /spine/curator` |

Reader-side control over how much a contract tells you — issue #155's
first finding, which was fanout with no reader control. The default is
already quiet: you hear nothing about a contract unless you authored
it, in which case you hear its lifecycle.

`all` is every authoritative event on the contract; `lifecycle` is
state changes only; `none` is silence. Deltas are batched per sweep
tick, so a busy contract cannot spam a subscriber, and they carry an
id, a title and what changed — never the contract text again.

**What no level can silence:** anything that names you personally — an
ask addressed to you, a verdict on a contract you are assigned, a
ruling on an ask you raised, an ask redirected to you. Those are
class-1 injections and they never yield to a subscription, because
they are claims on you rather than a broadcast you opted into.

## Spine tools (permission-gated)

### contract_author

| | |
|---|---|
| **Required permission** | `spine.author` |
| **Input** | `{ subject, title, criteria: [{id, text}], assignee, verifier?, authority?, constraints?: string[], subject_type?, subject_parent?, op_id? }` |
| **Output** | The contract id, its criteria ids, who is bound, and what completion will require |
| **Broker call** | `POST /spine/subjects` (when `subject_type` is given), then `POST /spine/events` (kind `specification`) |

The destination photograph. No length cap on criteria — a cap that
punishes precision buys nothing. Naming a `verifier` means completion
will need verdicts covering every criterion at one revision; naming
none means the result stands alone and says so. `subject_type`
registers the subject inline, per the design's rule that
member-referenced subjects are registered explicitly, at first use or
inline here.

### contract_amend

| | |
|---|---|
| **Required permission** | `spine.author` |
| **Input** | `{ contract, changes, reason, disposition: 'correction'\|'scope_change', title?, criteria?, constraints?, disclosure?, cites?, expected_state_rev, op_id? }` |
| **Output** | The new contract version and where the counter stands |
| **Broker call** | `POST /spine/events` (kind `amendment`) |

`criteria` and `constraints` are COMPLETE replacements, not patches.
Two refusals worth knowing before calling: removing text without a
`disclosure`, and dropping a criterion that already carries a verdict
without citing that verdict. Neither refuses the change itself — they
stop it happening quietly. `disposition` is the same field with the
same meaning as `objectives_amend` and `process_document_write`.

## Team admin tools (gated on `team.manage`)

Team-level config and permission presets. Reads are open on the
HTTP API, but the tools only surface to `team.manage` holders so the
toolbox stays narrow — any agent can pull team data from its
instructions. A `context` edit is instruction-bearing: the broker
fans it out and each affected runner restarts its agent at the next
idle boundary, resuming the same conversation under the new composed
text; the roster lists those members restart-pending until it does
(the `team_update` result restates this to the calling agent).

| Tool | Input | What it does |
|---|---|---|
| `team_get` | `{}` | Read the current team config: name, context (with size metrics), preset names. `GET /team`. |
| `team_update` | `{ name?, context? }` (at least one) | Update team-level fields. Returns the updated config. `PATCH /team`. |
| `presets_list` | `{}` | List presets as `{ name, permissions[] }`. `GET /team/presets`. |
| `presets_set` | `{ name (req), permissions: string[] (req, leaves only) }` | Create or replace a preset; members referencing it re-resolve on next read. Unknown leaves rejected. `PUT /team/presets/:name`. |
| `presets_delete` | `{ name (req) }` | Delete a preset (no soft-delete). Returns the members still referencing it — their resolved permissions silently drop its leaves on next read. `DELETE /team/presets/:name`. |

## Member admin tools (gated on `members.manage`)

Live member management from the agent toolbox. The broker enforces
the permission independently on every call.

| Tool | Input | What it does |
|---|---|---|
| `members_add` | `{ name (req), title (req), description?, instructions?, permissions?: string[] }` | Create a member. `permissions` accepts preset names or leaves. Returns the member plus the plaintext bearer token — emitted exactly once. `POST /members`. |
| `members_update` | `{ name (req), title?, description?, instructions?, permissions?: string[] }` | Update role, instructions, or permissions. Role and instructions edits fan out as an instructions event: the member's runner restarts its agent at the next idle boundary with the new composed text (a role edit also reaches teammates whose roster line changed). Enforces "at least one `members.manage` holder remains". `PATCH /members/:name`. |
| `members_remove` | `{ name (req) }` | Delete a member; all bearer tokens revoked. Refused if it would leave zero `members.manage` holders. `DELETE /members/:name`. |

## Tool-source admin tools (permission-gated)

Members holding `tools.manage` get the connector-lifecycle group —
the agent-authorship surface for
[tool sources](/docs/concepts/tool-sources). An admin agent can read
an API's docs, register a source, define its tools, bind members,
set a write-only credential, and iterate on failures without leaving
its toolbox. The broker enforces the permission independently on
every call.

| Tool | What it does |
|---|---|
| `tool_sources_list` | Registry overview: slug, kind, enabled, tool count, credential status. |
| `tool_sources_view` | One source's tools, bound members, config. Never the secret. |
| `tool_sources_create` | Register a `custom` or `mcp` source (slug immutable; binds nobody by itself). |
| `tool_sources_update` | displayName / enabled / allMembers / upstream url. |
| `tool_sources_delete` | Delete + cascade (bindings, credential, tool defs, cache). |
| `tool_sources_define_tool` | Set/replace a custom tool `{description, inputSchema, binding}`. The description teaches the full binding grammar inline. |
| `tool_sources_delete_tool` | Remove one custom tool def. |
| `tool_sources_bindings` | `add`/`remove` member access (mirrors `objectives_watchers`). |
| `tool_sources_set_credential` | Set/rotate the write-only credential (bearer or named header). The description warns that the secret enters the session transcript — when a human holds the key, they should drop it via the web UI instead. |
| `tool_sources_delete_credential` | Remove the credential. |
| `tool_sources_refresh` | Re-discover an mcp source's upstream tools. |

The intended authoring loop: define → bind yourself → call
`<slug>__<name>` → read the `isError` result (it carries the
upstream response) → redefine. Save-time validation failures name
the exact problem (origin drift, header shadowing, malformed
placeholders), so the loop converges fast.

## Secrets admin tools (gated on `secrets.manage`)

These appear only for members holding `secrets.manage` — the admin
surface for [secrets](/docs/concepts/secrets), broker-held values
injected as env vars on bound members' agent processes at runner
start. Values are write-only end to end; no tool ever returns one.

| Tool | What it does |
|---|---|
| `secrets_list` | Registry overview: slug, env var, enabled, value-set status. Never values. |
| `secrets_view` | One secret's metadata + bound members. |
| `secrets_create` | Register a secret (slug immutable; stores no value, binds nobody by itself). Reserved env names are rejected with the reason. |
| `secrets_update` | envName / description / enabled / allMembers. |
| `secrets_delete` | Delete + cascade (value, bindings). |
| `secrets_set_value` | Set/rotate the write-only value. The description warns that the value enters the session transcript — when a human holds it, they should drop it via the web UI instead. |
| `secrets_delete_value` | Remove the stored value. |
| `secrets_bindings` | `add`/`remove` member delivery (mirrors `tool_sources_bindings`). |

Delivery is spawn-time only: every mutation's response reminds the
agent that members pick changes up on their next runner start.

## Variables admin tools (gated on `secrets.manage`)

The same gate and lifecycle as secrets, for the **non-secret** half
of the runner environment — see
[variables](/docs/concepts/variables). A variable's value is
readable, never KEK-encrypted, and never registered with the trace
redactor, so it appears verbatim in captured traces (git identity
belongs here; credentials never do). Secrets and variables share
one per-member env namespace: binding a collision fails with 409.
Delivery is spawn-time only — members pick changes up on their next
runner start.

| Tool | Input | What it does |
|---|---|---|
| `variables_list` | `{}` | Registry overview: slug, env var, enabled, allMembers — and the value itself. `GET /variables`. |
| `variables_view` | `{ slug (req) }` | One variable's metadata, bound members, and value. `GET /variables/:slug`. |
| `variables_create` | `{ slug (req), envName (req), description?, allMembers? }` | Register a variable (slug immutable; same envName grammar as secrets; stores no value, binds nobody by itself). `POST /variables`. |
| `variables_update` | `{ slug (req), envName?, description?, enabled?, allMembers? }` | Update mutable fields. `PATCH /variables/:slug`. |
| `variables_delete` | `{ slug (req) }` | Delete + cascade (value, bindings). `DELETE /variables/:slug`. |
| `variables_set_value` | `{ slug (req), value (req) }` | Set the readable value — not a place for credentials. `PUT /variables/:slug/value`. |
| `variables_delete_value` | `{ slug (req) }` | Remove the value; the variable delivers nothing until a new one is set. `DELETE /variables/:slug/value`. |
| `variables_bindings` | `{ slug (req), add?: string[], remove?: string[] }` | Add/remove member bindings; 409 on env-name collision across the two stores. Returns the resulting bound set. `POST` / `DELETE /variables/:slug/bindings...`. |

## External notification admin tools (gated on `notifications.manage`)

These appear only for members holding `notifications.manage` — the
admin surface for
[external notifications](/docs/concepts/external-notifications),
inbound webhooks/API calls verified at `POST /hooks/<slug>` and
routed to members and channels as ambient input. This is the
self-provisioning surface: an agent can wire an external system to
itself — register the endpoint targeting its own name, set the
signing secret, hand the sender the hook URL, then debug with
delivery receipts and replay. Signing secrets are write-only end to
end; no tool ever returns one.

| Tool | What it does |
|---|---|
| `notifications_list` | Registry overview: slug, targets, scheme, policy flags, secret-set status. |
| `notifications_view` | One endpoint's full config: ingress URL, verification, filters, template, policy. |
| `notifications_create` | Register an endpoint (slug immutable — it is the URL). Targets are `"@member"` / `"#channel"` strings; auth/policy fields are flattened scalars. Stores no secret — the endpoint rejects everything until one is set. |
| `notifications_update` | Targets, verification, filters, template, policy, enabled. |
| `notifications_delete` | Delete + cascade (receipts, queued deliveries). The URL then 404s. |
| `notifications_set_secret` | Set/rotate the write-only signing secret. The description warns the value enters the transcript — fine for self-minted secrets; human-held ones should go in via the web UI. |
| `notifications_delete_secret` | Remove the secret (the endpoint then fails closed). |
| `notifications_deliveries` | Receipts, newest first — including rejected ones with the verification-failure reason the sender never sees. |
| `notifications_replay` | Re-run a stored delivery (verify/dedupe/rate-limit skipped; filters/template/policy apply). |
| `notifications_profiles` | List shared auth profiles + reference counts. |
| `notifications_profile_create` | Register a profile (one secret shared by several endpoints). |
| `notifications_profile_delete` | Delete a profile; refused while referenced. |
| `notifications_profile_set_secret` | Set/rotate the shared secret — re-keys every referencing endpoint. |

The operating loop mirrors connector authorship: create → set
secret → point the sender at the hook URL → watch
`notifications_deliveries` for rejected/filtered receipts → adjust
filters/template → `notifications_replay` to confirm without
waiting for the sender to fire again.

## State freshness

Tool descriptions are **static** for the lifetime of a session. The
only interpolation is boot-stable and functional (the member's fs
home path, permission-scoped wording) — never live state, and never
identity/roster prose (that lives in the system-prompt
instructions). Mutating descriptions mid-session would invalidate
the model's prompt-prefix cache, so state freshness rides message
traffic instead:

- **Objective lifecycle events** (assigned / blocked / completed /
  cancelled / reassigned) arrive as ordinary channel notifications
  the moment they happen.
- **Context refreshes** — the runner re-asserts the open plate with
  a `context_refresh` channel push (tagged
  `meta.kind = "context_refresh"`, `meta.from = "csuite"`) at
  session attach (first `tools/list` on a fresh bridge connection)
  and after context compaction (SessionStart hook with
  source=compact|clear). Empty plates are skipped.

The runner's objectives tracker keeps the open-plate snapshot fresh
(debounced 150ms to coalesce bursts) — it seeds the context refresh
and the objective_open/close activity markers.

`notifications/tools/list_changed` fires only for genuine
capability changes: when a `tool_source` registry event changes the
member's resolved external-tools set, the runner refetches its
instructions and emits it so the agent re-lists. See
[tool sources](/docs/concepts/tool-sources).

Instruction edits are the one exception that does NOT ride message
traffic at all: a `kind: 'instructions'` event schedules a
drain-and-restart, and the successor session composes fresh tool
descriptions and a fresh system prompt from the refetched packet.

## Error semantics

All tools return a `CallToolResult` with `isError: true` on
validation failures or broker errors:

```
{ content: [{ type: 'text', text: '<error message>' }], isError: true }
```

Common error shapes:

| Error | Meaning |
|---|---|
| `TOOL: FIELD is required` | Validation: missing required input |
| `TOOL: invalid status 'S'` | Validation: enum mismatch |
| `attachment not found: PATH` | The runner couldn't `fs_stat` an attachment |
| `attachment is a directory: PATH` | Attachments must be files |
| `broker error STATUS: BODY` | The broker returned a non-2xx HTTP response |
| `TOOL: you do not have the required permission on this team` | Local permission re-check failed (the server is the authoritative gate) |
| `you are not a member of #SLUG` | `channels_post` from a non-member |

Spine refusals are different in kind, and the tools render them in
full rather than collapsing them to `broker error STATUS`:

| Code | HTTP | What comes back |
|---|---|---|
| `stale_state_rev` | 409 | Every authoritative event the caller missed, each with its captions and whole body, then the counter to retry with |
| `coverage_gap` | 409 | Every uncovered criterion, its text, and why it is uncovered |
| `citation_required` | 409 | Each unresolved ask whole — question, context, unblocks, authority — plus the containment scope that was searched |
| `idempotency_conflict` | 409 | The event the `op_id` already resolved to |
| `invalid_transition` | 409 | The terminal state, and the delta when the caller was also behind |
| `invalid_input` | 400 | The schema issues, by field path |
| `not_permitted` | 403 | A structurally illegitimate act (assignee verdict, ruling by a non-authority) |

None of these is truncated. The refusal is the recovery channel — it
arrives at exactly the moment stale beliefs would have caused harm, and
a caller who has to make a second call to find out what they raced has
been told there is a problem and not what it is.

## Why broker → agent uses notifications, not tool calls

A tool call requires the agent to decide to call the tool. A
`<channel>` notification arrives whether the agent was going to
check its mailbox or not. That's the point: push, not poll.

Tool calls are the right primitive for **agent → broker** pushes
(every send / broadcast / objectives_* call IS a tool call). The
asymmetry is intentional — broker → agent is push, agent → broker
is pull.

For the wire-level shape of how notifications cross the runner ↔
bridge boundary, see [dev/ipc-protocol](/docs/dev/ipc-protocol).
