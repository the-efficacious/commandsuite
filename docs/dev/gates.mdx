# Gates, and what each one has been shown

A gate that has only ever run against work its author believed was good has been
tested in no directions. Its green is an opinion.

This page is the record of which of ours have been falsified — shown an input we
know is bad, and observed to fail — and which have not. It exists because three
of our own instruments were found defective in a single night, each by someone
using it for real rather than by the instrument itself:

- a liveness probe that printed `CONFIRMED` against an unchanged broker, because
  it grepped rendered output and matched its own fixture's role title;
- a query-plan tripwire that closed the statement it was written for and not the
  class of statement;
- the route walk, which asserted that the app shell had mounted and therefore
  passed a build with a page deleted from the router, and which discarded the
  console errors, failed requests and page text it had collected on the only
  path where they mattered.

## The practice

**An instrument earns its verdict by being shown a known-bad input, and until it
has been, a green from it is an opinion.** Four minutes each. Three rules follow
from doing it, and each was learned by getting it wrong first:

**1. Prove the input was actually bad.** A mutation you did not confirm reached
the system under test is not a test — it is the instrument agreeing with you
through a different door. Use a **build fingerprint that changes when your
change arrives**: the served asset hash, a version string, a checksum, whatever
the system offers. Deleting a route from the router and rebuilding with a pnpm
filter that matched no project produced a "known-bad build" that was byte-identical
to the good one, and a gate that passed it correctly.

```
asset before:  /assets/index-C1-T_VNZ.js
asset after:   /assets/index-C1-T_VNZ.js     ← nothing was tested
asset after:   /assets/index-DtYccP1C.js     ← now it is a different build
```

**2. Never discard stderr.** pnpm printed `No projects matched the filters`. It
went to `/dev/null`, and the exit code was checked instead. **Discarding stderr
is discarding the only channel that reports the thing you did not anticipate**,
which is by definition the thing you most need. This is a strictly worse failure
than an untested instrument: the information existed, was correct, was free, and
was thrown away by habit.

**3. A new check's first duty is to disagree with something you already know the
answer to.** The route walk's own marker-ambiguity check passed everything on
its first run — it read the page before its panels resolved, so a half-rendered
page flagged nothing. A self-check that self-approves is the failure mode this
whole practice has to survive. Point it at a case whose answer you already know,
and require it to disagree.

And the rule these serve: **the gate bends, not the security posture.** When an
instrument makes a correct property look expensive, fix the instrument.
`Cache-Control: no-store` made a route walk six times slower because Chromium
never reports those requests as finished ([#278](https://github.com/the-efficacious/commandsuite/issues/278));
the walker's idle rule changed, the header did not.

## The inventory

Falsified means: shown an input known to be bad, and observed to fail on it.

Required means: the platform refuses the merge if it fails. **Most of these are
not.** Per Lea's audit of the effective branch rules on 2026-08-31, the only
required status check on this repository is `route-walk`; nothing here requires
a pull request or an approving review either. I cannot verify that myself — this
seat's token cannot read branch protection — so it is recorded as her
measurement, not mine.

### A workflow that exists is not a gate

**`version-guard` is not required, so today nothing refuses a merge that fails
it.** It runs, it reports honestly, and the platform does not care — which makes
it, exactly, a green tick nobody has to obey. It becomes machinery when it is
added to the required status checks; that needs admin rights this seat does not
have.

Stated here rather than left implicit because the guard was built *in response
to* a convention wearing the appearance of a gate, and shipping it unrequired
would reproduce the thing it was built to close. The same applies to every row
above marked "no": those checks are useful, they are run, and a red one blocks
nothing but a reviewer's judgement.

And the rung below that, which no configuration reaches — **even where the
machinery is real, its coverage is convention.** A required check aggregates
whatever a file we control tells it to. For this repository the coverage of
`route-walk` is itself enforced (`contract.mjs` validates the manifest against
the router's `Route` union in both directions — a page added without a
declaration fails by name), but what each row *asserts* is enforced only as far
as the marker rules go, and whether a marker is a *good* one is review. A
force-push is a single detectable operation; "the work was checked" is a
judgement about coverage, and no ruleset holds that for us.

### `release`, in full

There is nothing to falsify about **what** it publishes, and that is a real
answer rather than a gap:

- **OIDC trusted publishing, with no npm token anywhere.** Each package's
  Trusted Publisher on npmjs.com is pinned to this repository *and this
  workflow file*. A fork, a different workflow, or a stolen secret cannot
  publish, because there is no secret.
- **Provenance is attached automatically**, linking each tarball to the exact
  commit it was built from — so an unexpected publish can be traced to its
  source after the fact.
- **`scripts/publish-gate.mjs check`** runs as every package's
  `prepublishOnly`: refusal-only, never rebuilds, and refuses a payload whose
  digest does not match the one recorded for HEAD. Its own header names the
  single path it cannot reach — `npm publish an-already-built.tgz` skips
  lifecycle hooks — which is why provenance, not another entry point, closes it.

**When** it publishes is a different matter, and is a convention rather than a
mechanism. `changeset publish` publishes any package whose version is not yet on
the registry, and the workflow runs on every push to `main`. So the trigger for a
release is *"a commit on main left a version npm doesn't have yet"* — **not a
human signature.** Versions changing only via the changesets Version PR is a
practice, not something the machinery enforces: an ordinary PR that edited a
version field, reviewed and merged in the normal way, would publish on merge.

So the claim "what shipped is what was on main at an attested commit" is
structurally true. The claim "nothing publishes without a human release
sign-off" rests on nobody merging a version change, and we would learn of a
violation only afterwards, from provenance or from npm. **That is a convention
wearing the appearance of a gate** — recorded here rather than assumed. Closing
it would mean refusing a version change on any commit that is not the changesets
bot's own.

### What follows from the un-falsified rows

**A gate we cannot falsify is a gate whose green is an opinion, and no release
claim may rest on one.** `codeql` and `dependency-review` are useful and stay;
what they are not is evidence. If a release note wants to say "no known
vulnerable dependencies ship in this release", that claim needs to name the
check that was run and shown to discriminate — not the presence of a green tick
from a gate nobody has ever seen fail.

The same applies to `release`, `bootstrap`, `container` and `docs-deploy` until
someone does the four minutes.

## Adding a gate

A new gate is not done when it passes. It is done when you have watched it fail
for the reason it exists, and the failure named the cause. Record the input and
the output in the table above in the same change that adds it.
