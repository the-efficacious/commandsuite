# Gates, and what each one has been shown

A gate that has only ever run against work its author believed was good has been
tested in no directions. Its green is an opinion.

This page is the record of which of ours have been falsified — shown an input we
know is bad, and observed to fail — and which have not. It exists because three
of our own instruments were found defective in a single night, each by someone
using it for real rather than by the instrument itself:

- a liveness probe that printed `CONFIRMED` against an unchanged broker, because
  it grepped rendered output and matched its own fixture's role title;
- a query-plan tripwire that closed the statement it was written for and not the
  class of statement;
- the route walk, which asserted that the app shell had mounted and therefore
  passed a build with a page deleted from the router, and which discarded the
  console errors, failed requests and page text it had collected on the only
  path where they mattered.

## The practice

**An instrument earns its verdict by being shown a known-bad input, and until it
has been, a green from it is an opinion.** Four minutes each. Nine rules follow
from doing it, and every one was learned by getting it wrong first:

**1. Prove the input was actually bad.** A mutation you did not confirm reached
the system under test is not a test — it is the instrument agreeing with you
through a different door. Use a **build fingerprint that changes when your
change arrives**: the served asset hash, a version string, a checksum, whatever
the system offers. Deleting a route from the router and rebuilding with a pnpm
filter that matched no project produced a "known-bad build" that was byte-identical
to the good one, and a gate that passed it correctly.

```
asset before:  /assets/index-C1-T_VNZ.js
asset after:   /assets/index-C1-T_VNZ.js     ← nothing was tested
asset after:   /assets/index-DtYccP1C.js     ← now it is a different build
```

**2. Never discard stderr.** pnpm printed `No projects matched the filters`. It
went to `/dev/null`, and the exit code was checked instead. **Discarding stderr
is discarding the only channel that reports the thing you did not anticipate**,
which is by definition the thing you most need. This is a strictly worse failure
than an untested instrument: the information existed, was correct, was free, and
was thrown away by habit.

**3. A new check's first duty is to disagree with something you already know the
answer to.** The route walk's own marker-ambiguity check passed everything on
its first run — it read the page before its panels resolved, so a half-rendered
page flagged nothing. A self-check that self-approves is the failure mode this
whole practice has to survive. Point it at a case whose answer you already know,
and require it to disagree.

**4. A red only counts as falsification if the control passed.** Run the
unmodified tree first and see it green; only then does a red on the mutated tree
mean what you want it to mean. The docs build died on a missing `node_modules`
*before it ever reached* the frontmatter I had broken — the exit code alone
would have read as a successful falsification, and "docs-deploy refuses a
missing title" would have gone into the table on evidence that proved only that
a workspace wasn't installed. **An environment failure wearing a falsification
is the mirror image of rule 1**: there, nothing was tested and the gate passed;
here, nothing was tested and the gate failed. Both look like results.

**5. Your own tools are part of the environment you are measuring.** Shell
`grep` on an agent seat here is not GNU grep — the harness shims it to `ugrep`
via a shell function, and the two disagree. On identical input:

```
printf '644 a\n600 b\n' | grep -vq '^600 '          → exit 1   (shimmed)
printf '644 a\n600 b\n' | command grep -vq '^600 '  → exit 0   (GNU, what CI and scripts run)
```

That difference nearly produced a false security finding: an assertion in
`compose-check.sh` that the secret files are mode `0600` appeared to pass on a
`644` fixture, which would have been reported as a gate that cannot fail. It
fails correctly under the grep that actually runs it. **A shell function is not
the binary a script invokes**, so when a result turns on a tool's exit code,
re-run it with `command <tool>` before believing it.

**Coverage differs too, and this one bites the way you look for things.** The
shim passes `--ignore-files`, so a recursive search *from the repository root*
silently skips everything `.gitignore` covers — `dist/`, `node_modules/`, build
output, logs. The ignore file binds to the search root, so searching a
subdirectory does not apply it:

```
marker in packages/core/dist (gitignored)     shimmed   GNU
  grep -rl … .                                     0      1     ← absence is a lie
  grep -rl … packages/                             1      1
  grep -rl … packages/core/dist                    1      1
```

So **"I grepped from the repo root and found nothing" is not evidence of
absence** on these seats — it is evidence of absence outside `.gitignore`. That
is usually what you want when reading source and exactly what you don't want
when asking whether a built artefact, a lockfile or a log contains something.

**And a corollary that cost more than the shim did.** Chasing the above, the
team adopted "use `! grep -q -E …`, never `grep -vq`". That is right for a check
list and **inverts a conformance audit**: applied to the mode assertion in
`compose-check.sh`, it silently permits a world-readable token. Measured under
GNU grep, modes `644` and `600`:

```
grep -vq '^600 '   → refuses ✓        ! grep -q '^600 '   → permits ✗
```

`grep -v` inverts **per line**, so it answers *does some line differ*, never *do
all lines conform*. Match the question to the assertion — *is any line bad?* is
`! grep -q`; *is any line not good?* is `grep -vq`. They coincide exactly when
input and intent are both single-line, which is why the wrong one survives
review. **A rule applied to the wrong shape doesn't fail loudly; it inverts and
looks tidier than what it replaced.**

**6. Make a vacuous control impossible, not merely noticeable — and we already
had the mechanism.** A control that perturbs a construct must **assert it found
the construct**, and stop if it did not:

```python
if old not in text:
    raise SystemExit(f"{label} control could not find the construct it is meant to perturb")
```

Without that line, a matcher that silently matches nothing produces a control
that "passes" having tested nothing. **Require both a non-zero exit and the
expected message**, or a check failing for an unrelated reason gets recorded as
the control firing.

**`scripts/mutate.sh` has done exactly this since 2026-08-01** — it diffs against
the original, prints `MUTATION DID NOT APPLY — the result would be meaningless,
so nothing ran`, and exits 2 without running the suite. It was written after a
mutation silently failed to apply over an indentation mismatch and a guard was
nearly reported as verified without ever being exercised.

**And it is referenced by nothing.** Not this page, not a workflow, not another
script. **The mechanism was correct, present, and invisible for a month** — so
three instruments written since then did not get it, and the failure it prevents
happened twice in one evening to the person who had read the rule:

```
a settlement control sealed with unsettled=0   -> passed, tested nothing
a checker printed "replay: 0 of 0"  twice      -> passed, tested nothing
```

**Both were caught by a person noticing.** That is the gap this rule closes, and
the gap was never the tooling — **it was that a working mechanism had no surface
in the practice, so new instruments were written without it.** Use `mutate.sh`
where it fits; where it doesn't, assert the construct yourself.

*(The rule was written down on the TurnDB side by Seamus, for a mechanism this
repo already had. A mechanism nobody writes the rule for does not travel.)*

**7. A check must discriminate, not merely respond.** Exercise it in both
directions before trusting it — the present case *and* the absent case:

```
present → 200        absent → 404
```

**A 200 for something that exists proves the URL is well-formed and says nothing
about whether the check would notice the thing missing.** The 404 is what makes
it an observation rather than a formality. This is rule 3 turned from "disagree
once" into "disagree on demand, both ways". *(Turner, testing an observation
endpoint against the real version.)*

**8. State which claim the check makes, at the check.** Two surfaces that look
equivalent can prove different things: an exact-version registry document says
*the version exists*; the packument says *an install would resolve it*. **They
diverged by fifteen minutes in a measured instance.** A green check is read as
the stronger claim unless it says otherwise, so write the narrower one down where
the result is produced:

> This proves registry existence, not packument propagation or npm installability.

**9. A check that fails on correct behaviour destroys the signal it was added
for.** A naive "fail on any non-success dependency" would have gone red on every
legitimate narrow run. **People learn to read red on that path as normal, which
is the condition under which a real red gets waved through.** The fix is not a
looser threshold — it is stating the property precisely enough that the mechanism
can deliver exactly it. *(Turner.)*

And the rule these serve: **the gate bends, not the security posture.** When an
instrument makes a correct property look expensive, fix the instrument.
`Cache-Control: no-store` made a route walk six times slower because Chromium
never reports those requests as finished ([#278](https://github.com/the-efficacious/commandsuite/issues/278));
the walker's idle rule changed, the header did not.

## Stating a gate: name the ladder, not the yes/no

**A gate described as a single yes/no is almost always a ladder with the bottom
rung missing.** That is how "we require review" and "our tests gate merges"
manage to be true-sounding and unfalsifiable at once: each names a real
mechanism and quietly implies coverage the mechanism never had.

So when claiming a gate — here, in a release note, or to anyone outside the
work — **list the rungs, name what refuses each one, and say plainly where
judgement begins.** For `route-walk` on this repository:

| rung | refused by |
| --- | --- |
| `route-walk` must pass | the platform (one of five required contexts) |
| every route in the router is walked | `contract.mjs`, validating the manifest against the `Route` union in both directions |
| a clean row asserts view content, not the shell | `contract.mjs` |
| the marker actually distinguishes that view from the fallback | the walker, against home's real text, before every run |
| the marker means the page *works* | **judgement — nothing refuses this** |

Two things follow, and the second is the one worth keeping.

**Coverage lives in files we control, so it is convention unless something
checks it.** A required check aggregates whatever its workflow says it does;
delete a job from the list and the platform still sees green, because the
enforcement was never about that job. Where coverage *is* mechanised — the
`contract.mjs` rung above — say so, because that is the rung people assume and
rarely verify.

**The bottom rung being judgement is not a defect to engineer away — it is what
review is for.** The point of mechanising the rungs above it is not to approach
zero judgement; it is to stop spending judgement on things a machine can hold,
so it is available for the one that needs a person. A reviewer asking "is this
marker a good assertion?" is worth something. A reviewer also expected to
remember whether the route was covered at all is a reviewer who will eventually
forget.

## The inventory

Falsified means: shown an input known to be bad, and observed to fail on it —
**with a control run on the unmodified tree observed to pass first**, so the red
is the mutation and not the environment.

Required means: the platform refuses the merge if it fails. **Enforcement here
comes from two layers, and reading either one alone gives a wrong answer.**
Measured:

```
GET /repos/…/rulesets            ruleset 21876976, active:
                                   deletion, non_fast_forward,
                                   required_status_checks: route-walk
GET /repos/…/branches/main       protected: true, enforcement: non_admins
                                   contexts: build, Verify Signed-off-by,
                                             dependency-review,
                                             Analyze (javascript-typescript)
GET /repos/…/branches/main/protection      404 — admin-gated
```

**Five required contexts, not one.** Every audit of this repository tonight —
three people, independently — read one source and reported it as the state of
the world. turndb enforces through rulesets alone and commandsuite through
classic protection with a ruleset on top, so the *same* endpoint honestly
answers "the enforcement" on one repo and "some of the enforcement" on the
other. That needed a second source, not more care with the first.

When `branches/{branch}/protection` 404s, **read `branches/{branch}`** before
concluding you cannot see: it carries a `protection` summary including
`required_status_checks.contexts`.

| --- | --- | --- | --- | --- |

| `route-walk` | **yes** | same | a broker without `Vary: Accept` ([#276](https://github.com/the-efficacious/commandsuite/issues/276)) | **Failed by name** on `objective-detail` — the page renders `invalid JSON` under HTTP 200 |

Also refuses the vacuous case: an empty `--pr-title` exits 1 rather than checking nothing and passing. It additionally self-tests its own fixtures in the same job, so a validator degraded to reject-everything fails there rather than blocking every PR. |
| `dco` | **yes** (`Verify Signed-off-by`) | every commit carries `Signed-off-by` | an empty commit created with `--no-verify` | **Failed**, naming the commit |
| `ci` (test suite) | **yes** (`build`) | the repository's tests | a fixture asserting `expect(1).toBe(2)` | **Failed** — `Test Files 1 failed (1)` |

Doing that means pushing a deliberately vulnerable pattern, which needs a decision, not an initiative. |
| `dependency-review` | **yes** | new dependencies with known advisories, OpenSSF thresholds | **cannot be falsified by me** | To falsify: add a dependency with a known advisory on a scratch PR. Same caveat. It *has* fired in anger — it rejected `puppeteer-core`, which is why the route walk drives raw CDP. |
| `release` | n/a | what gets published, and when | **structurally protected for *what*; the *when* is now guarded — see below** | A release is the human gate, so this row is longer than the others. |
| `version-guard` | **not yet — see below** | a version may only change via the changesets Version PR | a real `0.8.0 → 9.9.9` bump to `packages/core/package.json`, committed on an ordinary branch | **Refused**, naming the file, both versions and the branch. The same commit on `changeset-release/main` passes. Branches merely *named* like the release branch (`changeset-release/main-2`, `not-changeset-release/main`) are refused. Invoked without its arguments it exits 2 rather than reporting nothing to check. Its own fixtures run in the same job that enforces it. |

### A workflow that exists is not a gate

**`version-guard` is not required, so today nothing refuses a merge that fails
it.** It runs, it reports honestly, and the platform does not care — which makes
it, exactly, a green tick nobody has to obey. It becomes machinery when it is
added to the required status checks; that needs admin rights this seat does not
have.

Stated here rather than left implicit because the guard was built *in response
to* a convention wearing the appearance of a gate, and shipping it unrequired
would reproduce the thing it was built to close. The same applies to every row
above marked "no": those checks are useful, they are run, and a red one blocks
nothing but a reviewer's judgement.

And the rung below that, which no configuration reaches — **even where the
machinery is real, its coverage is convention.** A required check aggregates
whatever a file we control tells it to. For this repository the coverage of
`route-walk` is itself enforced (`contract.mjs` validates the manifest against
the router's `Route` union in both directions — a page added without a
declaration fails by name), but what each row *asserts* is enforced only as far
as the marker rules go, and whether a marker is a *good* one is review. A
force-push is a single detectable operation; "the work was checked" is a
judgement about coverage, and no ruleset holds that for us.

### `release`, in full

There is nothing to falsify about **what** it publishes, and that is a real
answer rather than a gap:

- **OIDC trusted publishing, with no npm token anywhere.** Each package's
  Trusted Publisher on npmjs.com is pinned to this repository *and this
  workflow file*. A fork, a different workflow, or a stolen secret cannot
  publish, because there is no secret.
- **Provenance is attached automatically**, linking each tarball to the exact
  commit it was built from — so an unexpected publish can be traced to its
  source after the fact.
- **`scripts/publish-gate.mjs check`** runs as every package's
  `prepublishOnly`: refusal-only, never rebuilds, and refuses a payload whose
  digest does not match the one recorded for HEAD. Its own header names the
  single path it cannot reach — `npm publish an-already-built.tgz` skips
  lifecycle hooks — which is why provenance, not another entry point, closes it.

**When** it publishes is a different matter, and is a convention rather than a
mechanism. `changeset publish` publishes any package whose version is not yet on
the registry, and the workflow runs on every push to `main`. So the trigger for a
release is *"a commit on main left a version npm doesn't have yet"* — **not a
human signature.** Versions changing only via the changesets Version PR is a
practice, not something the machinery enforces: an ordinary PR that edited a
version field, reviewed and merged in the normal way, would publish on merge.

So the claim "what shipped is what was on main at an attested commit" is
structurally true. The claim "nothing publishes without a human release
sign-off" rests on nobody merging a version change, and we would learn of a
violation only afterwards, from provenance or from npm. **That is a convention
wearing the appearance of a gate** — recorded here rather than assumed. Closing
it would mean refusing a version change on any commit that is not the changesets
bot's own.

### The grid: required × falsified

Two independent properties, and the interesting square is not the one people
look at:

| | **falsified** — shown a known-bad input and seen to fail | **unfalsified** |
| --- | --- | --- |
| **required** — can block a merge | what you want. Real authority, demonstrated. | **the worst square.** The authority is real and the demonstration is absent. |
| **not required** | useful, honest; a reviewer's judgement decides what to do with it | a green tick nobody has to obey and nobody has tested |

`codeql` and `dependency-review` are in the worst square: both are required
contexts on `main`, either can refuse a merge, and neither has ever been shown
to refuse anything. That is strictly worse than an unfalsified gate nobody
relies on, because a release claim can honestly cite a check that blocks — while
the evidence that it *would* block does not exist.

`version-guard` is in the bottom-right for the opposite reason: falsified
thoroughly, required by nothing.

**Falsifying the two in the worst square is scheduled work with boundaries, not
a spare-twenty-minutes job** (ruled by Lea, 2026-08-31), because it means
committing something deliberately bad to a public repository:

- a dedicated short-lived branch, never merged, deleted immediately after;
- the commit message and the fixture both stating in plain words that this is a
  deliberate gate test;
- a *known published* advisory or a canonical CodeQL test pattern — never
  something novel that could be mistaken for a real finding about our code;
- a named owner, done deliberately, recorded here with what was pushed and what
  refused — and not on a release night;
- anything that would raise an external notification (a security advisory, an
  org-wide alert) goes to Lea first.

### What follows from the un-falsified rows

**A gate we cannot falsify is a gate whose green is an opinion, and no release
claim may rest on one.** `codeql` and `dependency-review` are useful and stay;
what they are not is evidence. Note the uncomfortable pairing the measurement
produced: **both are *required* — they can block a merge — and neither has ever
been shown to fail.** Required and unfalsified is the worst square to be in,
because the authority is real and the demonstration is absent. If a release note wants to say "no known
vulnerable dependencies ship in this release", that claim needs to name the
check that was run and shown to discriminate — not the presence of a green tick
from a gate nobody has ever seen fail.

The same applies to `release`, `bootstrap`, `container` and `docs-deploy` until
someone does the four minutes.

## Reproducing these falsifications

Every row above was produced by one of these. They are here so the table can be
re-checked rather than believed, and so the next person adding a gate has a
worked example of the shape.

**`route-walk` — a page deleted from the router.** The asset hash is the
fingerprint proving the mutated build reached the browser; without it you may
be testing nothing (see rule 1).

```bash
curl -s "$URL/" | grep -oE '/assets/index-[A-Za-z0-9_-]+\.js'   # before
# in packages/web-ui/src/lib/routes.ts, make the objectives-list branch unreachable:
#   if (rest.length === 0 && false) return withTeam({ kind: 'objectives-list' }, team);
pnpm build                                                       # ROOT build; a filter may match nothing
curl -s "$URL/" | grep -oE '/assets/index-[A-Za-z0-9_-]+\.js'   # must differ
node scripts/route-walk/walk.mjs --broker "$URL" --member builder --role baseline \
  --secret "$WALK/totp-builder.secret" --fixtures "$WALK/fixtures.json" \
  --out /tmp/kb --only objectives-list
# expect: FAIL … [shell mounted but "outcome:" absent — wrong view for this URL]
```

**`route-walk` — a broker without the `Vary` fix.** Point the same walk at one:
`objective-detail` fails on its marker, because the page renders `invalid JSON`
under HTTP 200 with no console error and no failed request.

**`route-walk` — a marker that proves nothing.** Change any row's marker to a
string home also renders (`"ROSTER"`). The walk aborts before touching a route:
`these markers also appear on home, so they prove nothing`.

**`contract.mjs` — a page with no declaration.** Add a kind to the `Route` union
in `routes.ts` and run `node scripts/route-walk/contract.mjs --check
scripts/route-walk/manifest.json`. Expect `route kind '…' is in the router but
absent from the manifest`.

**`version-guard`.** Against the live Version PR and against the same commit
from anywhere else — the verdict must flip on the branch name alone:

```bash
node scripts/check-version-bump.mjs --base-ref origin/main --head <version-pr-sha> \
  --head-ref changeset-release/main        # exit 0
node scripts/check-version-bump.mjs --base-ref origin/main --head <version-pr-sha> \
  --head-ref feat/anything-else            # exit 1, naming every package
```

**`commit-convention`.** `node scripts/check-commit-convention.mjs --pr-title
"style(team): <74 chars>" --author <you>` — expect both `[length]` and
`[unknown-type]`. An empty `--pr-title` must exit 1, not pass vacuously.

**`dco`.** `git commit --allow-empty --no-verify -m "test: no trailer"`, then the
workflow's own loop over `git show -s --format='%(trailers:key=Signed-off-by,valueonly)'`.

**`ci`.** Drop a test asserting `expect(1).toBe(2)` and run it.

**`docs-deploy`.** Remove `title` from any page's frontmatter and run
`pnpm build` in `docs/site` — expect `InvalidContentEntryDataError … title:
Required`. Run the control first: that workspace has its own `node_modules`, and
a missing install fails the build for a reason that has nothing to do with your
mutation.

## Adding a gate

A new gate is not done when it passes. It is done when you have watched it fail
for the reason it exists, and the failure named the cause. Record the input and
the output in the table above in the same change that adds it.
