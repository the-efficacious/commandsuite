# Device enrollment

`csuite connect` is how a new device joins the team — your laptop, a
VM, a CI runner, a teammate's workstation. You approve it from the web
UI; the credential goes straight from the broker to the device. Nobody
copies a token through a clipboard, a screenshot, or a chat thread —
the surfaces where pasted credentials leak.

## Enroll a device

On the device:

```bash
$ csuite connect --url https://broker.example.com

  ┌─────────────────────────────────────────────────────┐
  │  visit:  https://broker.example.com/enroll?code=…   │
  │  code:   KQ4M-7P2H                                  │
  │  expires in 300s                                    │
  └─────────────────────────────────────────────────────┘
  waiting for approval... (press Ctrl-C to cancel)
```

Open the URL (it carries the code) or type the code at `/enroll` in
the web UI. Approving requires the `members.manage` permission and a
signed-in web session — the person running `csuite connect` can't
approve themselves.

The approval screen shows the request's source IP, user agent, and the
device's suggested label, and offers two choices:

- **Bind to an existing member** — the device becomes another token
  for that member. Their other devices keep working.
- **Create a new member** — name, role, permissions, and optional
  instructions, all set at approval time.

On approval, the CLI's next poll picks up the token and saves it to
the device's auth store (`~/.config/csuite/auth.json` on Linux),
scoped to the directory you ran `csuite connect` in — so one machine
can hold a different member identity per project. Pass
`--workspace <dir>` to scope it elsewhere, or `--global` for
machine-wide. `csuite auth list` shows what's enrolled where.

If nobody approves within five minutes, the request expires; run
`csuite connect` again.

Security properties, briefly: the credential travels only from broker
to device — the approver never sees it; the broker stores only hashes,
so an approved credential can't be re-read later; requests are
single-use, expire in five minutes, and minting is rate-limited per
IP. The handshake follows RFC 8628, the same device-code flow
`gh auth login` uses.

## Managing a member's tokens

A member can hold many tokens at once — one per enrolled device. The
web UI's Manage tab for each member lists them with label, origin,
created/last-used times, and a per-token revoke.

`csuite rotate --member <name>` is the break-glass: it revokes
**every** token the member holds and prints one fresh replacement.
Reach for it when you suspect a leak; for everyday "add a device," use
`csuite connect`.

## Web UI login

Enrollment covers devices running the CLI. Humans signing in to the
web UI use an authenticator app instead: `csuite enroll --member <name>`
prints a QR code to scan. Re-running it rotates the secret and
invalidates previously bound authenticators. Anyone holding
`members.manage` can re-enroll a member who's locked out.

## When approval isn't possible

If no approver is reachable — say, provisioning an air-gapped CI
runner — fall back to handing the token over yourself:

```bash
# On a machine with a credential holding members.manage:
csuite rotate --member ci-runner    # prints the new token once

# On the device:
export CSUITE_TOKEN='csuite_…'
```

You're back to hand-carrying a credential, so prefer `csuite connect`
whenever a live approval is possible.

## Troubleshooting

- **`enrollment expired`** — nobody approved within five minutes. Run
  `csuite connect` again.
- **`rejected`** — the approver hit Reject. If it was a misclick, just
  retry.
- **HTTP 429 on connect** — too many enrollment attempts from this IP
  in the last hour. Wait it out.
- **Token saved but commands still ask for one** — either
  `$CSUITE_TOKEN` is set (it wins over the saved entry), or the URL
  you're using doesn't exactly match the one you connected with (the
  lookup is exact-match, including trailing slashes).
