# Troubleshooting

## Broker reachability

### `briefing failed against <url>: ECONNREFUSED`

The runner couldn't reach the broker. The most common cause:

```bash
csuite serve  # in a separate terminal
```

If the broker is meant to live elsewhere, check `--url` and
`$CSUITE_URL`. The runner falls back to `http://127.0.0.1:8717` when
neither is set.

### `failed to reach broker at <url>: fetch failed`

Network / DNS / TLS issue. Verify with:

```bash
curl <url>/healthz
```

For self-signed certs (LAN deployments) you'll need to use the
broker's HTTPS port and either trust the cert in your system
store or run with `NODE_TLS_REJECT_UNAUTHORIZED=0` set in the CLI's
own env. (This affects only the CLI's connection to the broker; the
runner doesn't intercept the agent child's network traffic at all —
trace capture consumes each agent's native instrumentation instead.)

### `--token or CSUITE_TOKEN is required`

No bearer token resolved. Three sources, in order:

1. `--token <secret>` flag
2. `$CSUITE_TOKEN` env var
3. Saved entry in `~/.config/csuite/auth.json` for the resolved URL

Run `csuite connect` to enroll the device, or pass the token
explicitly. **If `auth.json` has an entry but the CLI doesn't
find it**, the URL is probably mismatched — the lookup is
exact-match (no trailing-slash normalization). Check what URL
you connected with versus what URL you're using now.

## --doctor failures

### `[FAIL] claude binary`

Claude Code ships bundled with the CLI, so this usually means a
broken or partial install — reinstall csuite on this platform. If
`$CLAUDE_PATH` is set, it must point at a real executable; a stale
override fails rather than falling back:

```bash
unset CLAUDE_PATH   # to use the bundled Claude Code
```

### `[FAIL] codex binary`

Codex is not bundled: the runner checks `$CODEX_PATH` first, then
`which codex`. Install it (`npm i -g @openai/codex`) or set
`$CODEX_PATH` to the absolute path.

### `[FAIL] $TMPDIR writable`

The runner writes scratch files to `$TMPDIR` at `0o600`. Common
causes:

- `$TMPDIR` is set to a path that doesn't exist
- Filesystem mounted read-only
- Permission issue on the directory

Check with:

```bash
echo "$TMPDIR"
ls -ld "$TMPDIR"
```

Typically just unset `$TMPDIR` (so it falls back to `/tmp`) or
point it at a writable location.

### `[FAIL] loopback hook server bindable`

The runner couldn't `listen()` on `127.0.0.1:0`. Trace capture needs
a loopback port; sandboxed environments without loopback networking
trigger this — uncommon, some restrictive CI runners.

If you can't get loopback bind to work, you can run with
`--no-trace` to skip the hook server entirely. You lose trace capture
but everything else works.

## Port conflicts

### `EADDRINUSE: address already in use 127.0.0.1:8717`

Something else is already on port 8717. Either find and kill it,
or change ports:

```bash
csuite serve --port 8718
# or
CSUITE_PORT=8718 csuite serve
```

Then point your runners and CLI invocations at the new port:

```bash
csuite claude --url http://127.0.0.1:8718
# or
export CSUITE_URL=http://127.0.0.1:8718
```

## `.mcp.json` has a stale `csuite` entry

Current runners never touch `.mcp.json` (or anything else in your
working tree) — the agent's configuration travels in memory. If you
find a `csuite` entry in a project's `.mcp.json`, it was left by an
old version of csuite that rewrote the file and crashed before
restoring it. Delete the `csuite` server entry by hand; leave other
entries alone.

## Empty traces

### `Captured traces` panel is empty for a completed objective

Traces are captured from each agent's own instrumentation and
uploaded to the broker — see [trace capture](/docs/tracing). Common
causes for an empty panel:

1. **The session ran with `--no-trace`.** Nothing is captured.
   Re-run without the flag.

2. **The broker was unreachable or the token was wrong during the
   session.** Uploads were dropped. Check the runner's session log
   (`~/.cache/commandsuite/session-<pid>.log`) for upload errors, and
   the server log for rejected requests.

3. **The session produced no completed turns.** A session that
   started and exited without the agent doing anything has nothing
   to show.

## Activity DB grows unbounded

```bash
csuite prune-traces --older-than 30d
```

Deletes activity rows older than the cutoff. Set up a daily
cron:

```cron
0 3 * * *  csuite prune-traces --older-than 30d --yes
```

If the DB has already grown to many GB and you want to compact
the file after deleting, run a manual `VACUUM` on the activity
DB while the broker is offline:

```bash
sqlite3 ./csuite-activity.db 'VACUUM;'
```

WAL mode means online deletes don't shrink the file; vacuum
does, but it takes an exclusive lock.

## Encryption key trouble

### `KekResolutionError: cannot decrypt totpSecret`

The key file (`csuite-kek.bin`, next to the server config) is
missing or wrong, OR `$CSUITE_KEK` is set to the wrong key. Two
recovery options:

- **Restore the original key file** from backup if you have one.
  Without it, encrypted fields can't be recovered.
- **Reset the encrypted state**: re-enter every stored secret value,
  re-enroll TOTP for every member (`csuite enroll --member <name>`
  for each), and let web push regenerate its keys (browsers will
  need to re-subscribe).

To avoid this in production, inject `$CSUITE_KEK` from a real
secrets manager rather than relying on the auto-generated file.

### Lost the database but still have the key

The team lives in the database, so this is a start-over:
`csuite setup` builds a fresh team, then re-issue every credential
and re-enroll every authenticator. The key on its own isn't useful
without the encrypted data it wrapped.

## TOTP rate limits

### `429 Too Many Requests` on /session/totp

Per-member: 5 failures / 15 minutes. Global (codeless login,
where the server iterates members to find a match): 10 failures
/ 15 minutes.

Wait the window out. If you're locked out and need to bypass:

```bash
csuite enroll --member <name>
```

re-enrolls the member with a fresh secret. Any member holding
`members.manage` can run it, so an admin can always recover a
locked-out teammate.

## Token rotation

### Suspecting a token leak

```bash
csuite rotate --member <name>
```

Revokes **every** active token for the named member and mints a
fresh one. Print is one-shot; save the new token immediately.

Every existing process holding the old token starts failing on
its next request. Re-enroll affected devices with `csuite connect`.

### `--reveal-token` printed something then everything broke

`csuite roster --reveal-token --member <name>` is an alias over
`csuite rotate`. It rotates as a side effect. Any process using the
previous token (CI runners, scripts) is now broken — they need
the new value. The CLI print is your only chance; if you missed
it, run rotate again.

## `csuite setup` refuses to run

### `setup: <path> already points to a populated team`

Setup refuses to overwrite — running it would mint a fresh admin
and invalidate every existing token. Two options:

- **You really want to reset:** remove both the config file and the
  database the message names (`rm csuite.json csuite.db`, or
  `rm -rf csuite/` if you're on the default directory layout) and
  run setup again. Every existing bearer token is invalidated;
  every TOTP enrollment is gone; you'll re-onboard everyone.
- **You meant to add a member:** use `csuite member create` instead.

## Codex-specific

### `csuite codex: no codex auth.json found in ~/.codex`

Codex isn't logged in. Run:

```bash
codex login
```

The runner reuses your real codex login, so `~/.codex/auth.json`
must exist before the first `csuite codex` run.

### `Refusing to create helper binaries under temporary dir`

This warning would fire if the runner's CODEX_HOME parent dir
were under `$TMPDIR`. We use `~/.cache/commandsuite/codex/` instead
specifically to avoid this — if you're seeing it anyway, check
`$XDG_CACHE_HOME` and make sure it doesn't point at a tmpfs.

## Runner problems

### `csuite mcp-bridge: CSUITE_RUNNER_SOCKET is required`

You ran `csuite mcp-bridge` directly. It's not meant to be invoked
manually — the runner injects it into the agent's configuration
automatically, with the right environment.

### Multiple runners stepping on each other

Each runner binds a unique socket at
`/tmp/.csuite-runner-<pid>.sock`. They don't interfere by path.
The single-bridge constraint is per-runner: if two MCP bridges
connect to the same runner, the older one is dropped.

To run multiple agents simultaneously, run multiple runner
processes in different terminals.

## Where to look for more detail

- **Session log**: `~/.cache/commandsuite/session-<pid>.log`
  — structured JSON per event. `tail -f` it during a run.
- **Server log**: stderr of `csuite serve`. Structured JSON;
  redirect to file in production.
- **`--doctor`**: covers the most common environmental failures
  before they bite you.

If a problem isn't covered here, the logs almost always have
enough to pin it down — the runner deliberately over-logs at
state transitions because the alternative is unhelpful "agent
just stopped working" reports.
